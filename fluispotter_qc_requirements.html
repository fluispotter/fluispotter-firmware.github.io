1. Document Overview

This document collects all testable mechanical and electrical requirements for the Fluispotter device, with the purpose of creating an automated device QC process: each requirement names the measurement method that verifies it and carries machine-readable pass/fail limit(s), so a QC runner can execute it against a physical device without judgement calls. Mechanical requirements are added as we go.

Each requirement is a single testable shall-statement with a stable ID, a class (MECH mechanical / ELEC electrical), a sub-system, a measurement method, and named limits. A limit value of TBD marks a requirement whose threshold is not yet fixed — it is listed but not yet enforceable in automated QC. This document is generated from the machine-readable registry verification/qc_requirements.py; the document and the registry cannot drift apart.

Each requirement also carries a lock status: a Locked requirement is frozen — its text changes only on the owner's explicit instruction, enforced by a content-hash baseline that fails the build on any unsanctioned edit or removal — whereas an Open requirement may still be revised. New requirements default to Open.

3. Automated QC & Traceability

The registry is machine-readable: an automated QC runner reads each requirement's method and limits directly from verification/qc_requirements.py, executes the named measurement against the device under test, and passes/fails it against the named limit(s). Requirements whose limits are still TBD are reported as NOT-ENFORCEABLE rather than silently passed, so threshold gaps stay visible until fixed from bench data.

Registry structure, doc mirroring, the lock baseline, and the change history are validated headlessly by the SW verification suite (SWR-513).
