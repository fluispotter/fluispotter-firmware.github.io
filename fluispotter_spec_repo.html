New §5.5.1 ULP Cooperative Scheduler — Non-Blocking Continuous Loop (ULP_Operational 1.17.0, promoted 2026-07-26 on the owner’s call). The co-processor no longer runs the §5.5 per-wake 1 ms tick in which dose (~10 s), coast (5 s), park (≤30 s) and parking calibration each spun INTERNALLY for the whole operation and owned the ULP: it is now ONE continuous, fully non-blocking loop in which every state (AC_RUNNING, BP_RUNNING, dose, coast, park, park-offset, parking calibration) advances by exactly one encoder/hall read per pass through a shared per-pass core (seg_pass), with the escalating spin-up kick folded per-pass too (try_kick_pass) — so the ULP blocks NOWHERE. The adaptive skip ladder is preserved as a WALL-CLOCK deadline and sched_idle() sleeps the loop between measurement bursts, keeping the battery profile; the BP hall is serviced at the TOP of every pass in EVERY state (SWR-289 strict); a mid-run stall power-cycles the DAC7574 driver on a non-blocking deadline (seg_recover) during which the OTHER pump is still serviced every pass (the 1.15.0 blocking version starved it for 200 ms). Parking calibration became the non-blocking BP_PARK_CAL state but keeps the EXACT SAME CPU contract (test_request = TEST_DETERMINE_PARKING → poll for TEST_NONE; publishes bp_hall_bracket_ticks, bp_park_offset_ticks = bracket/2, bp_park_enc_total) — no firmware change was needed. Benefits: the deep call chains behind the ULP stack-overflow class (GitHub #48) are gone, AC-hall edge loss during BP blocking windows ends, and the calibration encoder-edge undercount is removed at its source. Rollback is a single macro (ULP_FOLD_BUILD). The §5.5 note that the “#48 roll-in to operational ULP 1.16.0 is code-complete” is superseded: 1.16.0 was withdrawn and is burned/quarantined (it carried the ULP-side DEFEND_CLOCK, convicted as the #53 chronic-INT_WDT cause), which is why the promotion went 1.15.0 → 1.17.0.

4. Sensors & Electronics

4.1 VEML Light Sensor — Line Spot

Two VEML6035 ambient light sensors (Vishay). Designators: SPOT and LINE. The VEML6035 native I²C address is 0x29 (fixed); the LTC4316 translator (IC15) maps the pair onto the shared bus as SPOT = 0x3a, LINE = 0x29 (corrected 2026-06-15 — the two designations were previously reversed in software). I²C on SDA_GEN (GPIO38) / SCL_GEN (GPIO43). Enable: the SPOT/LINE emitter pair is powered by PIN_OUT_ENABLE_TAPE_EMITTERS (GPIO43, shared with the tape emitter), not GPIO48 — GPIO48 (PIN_OUT_ENABLE_FLUID_RECEIVERS) enables the blood/AC fluid receivers (see §4.5/§4.6). The prior “supply via GPIO48” was a misattribution; see the §4A.6 GPIO map for the authoritative assignment.

Read protocol (must configure first). The VEML6035 boots shut down (CONFIG register 0x00, bit 0 = ALS_SD) and returns no data until configured. Any reader (driver or host script) must first write CONFIG 0x00 to power it on — the firmware uses 25 ms integration time, gain/dg normal, sensitivity HIGH = 0x0300 — then read the ALS data at register 0x04 (16-bit little-endian) and scale lux = count × 0.0512 (the lux_resolution for that config, designingveml6035.pdf). Skipping the power-on, or reading the wrong register (e.g. 0x09), returns nothing — this was the root cause of a “no signal from the spot/line sensors” bug in the Control/Monitor sensor-monitor scripts (now fixed: they configure 0x0300 and read 0x04).

4.1b Analog Fluid + Pressure Sensors (ADC)

The Blood/air receiver (ADC GPIO7), AC/air receiver (ADC GPIO6) and the pressure sensor (ADC GPIO3) are read via machine.ADC(...).read_uv(). These ADCs must be created with atten=ADC.ATTN_11DB for the full 0–3.3 V range; the MicroPython default attenuation caps at ~0.95 V and would clip any reading above that (it left the firmware pressure reading clipped while the Control App, which already set ATTN_11DB, read the full range). Because read_uv() returns the calibrated true voltage for in-range signals, the air-sensor thresholds in board_config.py (blood: air > 800 mV, AC/water 500–800, blood < 500; AC: water < 500) are unaffected by the attenuation change.

Pressure sensor part & range. The pressure transducer is an NXP MPXV5004DP — a differential, dual-port sensor rated 0–3.92 kPa (≈ 0–39.2 mbar / 0–400 mmH&sub2;O / 0–29.4 mmHg / 0–0.57 psi). Its output is ratiometric: Vout = Vs·(0.2·P[kPa] + 0.2) — sensitivity 0.2·Vs per kPa, with a zero-pressure offset of 0.2·Vs (so ≈1.0 V at rest, ≈4.9 V full-scale on a 5 V supply). The firmware does no kPa conversion — PressureSensor.read_pressure() returns the raw read_uv() microvolts (the Sensors tab shows mV). Caveat: the ESP32 ADC tops out at ~3.3 V, so on a 5 V supply (consistent with the ~1 V resting reading that was being clipped above) only roughly the lower ~0–2.1 kPa of the rated span fits under the ADC ceiling; capturing the full 3.92 kPa needs a ~3.3 V sensor supply (full-scale ≈ 3.25 V) or an output divider — confirm the pressure rail.

5.5 ULP-RISC-V Pump Speed Controller (Simple-P 16-tick)

A fully autonomous pump speed regulation loop runs on the ESP32-S3 ULP-RISC-V co-processor, implemented in C (main.c) and loaded into RTC slow memory at boot. The loop operates independently of the main Xtensa cores while the device is in Light Sleep; both the blood pump and the AC pump are regulated. As of ULP_Operational 1.3.1 the steady-state speed regulation uses a Simple-P incremental control law over a 16-edge measurement window (“Simple-P 16-tick”), replacing the positional integer-tick PID of 1.2.4. The two blood-pump special modes — precision dosing (BP_DOSING) and hall parking/calibration (BP_PARKING) — retain the legacy positional PID (run_pid()), unchanged.

Execution model. The controller is tick-based: each ULP wake runs ac_tick() then bp_tick(), performing at most one measurement plus one power step per regulated tick, with all loop state held in RTC slow RAM between wakes — not a blocking loop.

Encoder sampling (N = 16, edge-locked). The ULP enables encoder power, polls the XOR quadrature signal (GPIO4 blood / GPIO16 AC), discards ENCODER_SKIP_PULSES = 1 turn-on edge, latches the timer on the next rising edge and times the interval across N = op_p_pulse_count = 16 rising edges, then disables the encoder. The wide 16-edge window (vs N=2 in 1.2.4) lowers per-sample jitter; a settled loop also services far less often via the skip ladder. Two decoupled deadlines bound a sample: a short first-edge window (calc_batch_timeout_us, ~50 ms floor, scaled with SPR) declares a true stall — no encoder edge at all — quickly, while a longer measurement window (calc_meas_timeout_us ≈ 4× the 16-edge time + 200 ms) bounds completion of a moving batch. So “encoder ticks never come in” is caught in ~50 ms regardless of the coarser measurement window.

Time base. Intervals are measured in raw ticks of the ESP32-S3 internal RC slow clock (CONFIG_RTC_CLK_SRC_INT_RC, ~136 kHz nominal ≈ 7.35 µs/tick) — not the 32.768 kHz crystal. The RC oscillator drifts (±~10 % over temperature/voltage) but is continuously calibrated: the runtime stores period (µs-per-tick × 219, Q13.19 fixed-point) in RTC_CNTL_STORE1_REG, which the ULP reads via rtc_cal_period(). Conversions (shift = RTC_CLK_CAL_FRACT = 19): ticks_to_us = (ticks × period) >> 19; us_to_ticks = (us << 19) / period. The controller and its setpoint both work directly in RC ticks, so calibration is applied once (when deriving the setpoint) and clock drift cancels in the error. sample_encoder() returns raw elapsed ticks (uint32, saturating at 0xFFFFFFFF); elapsed µs are still exported as telemetry (*_elapsed_us) via ticks_to_us().

Control law — Simple-P incremental (ULP 1.3.1). Each regulated measurement computes a percent speed error and nudges the accumulated motor power by a per-pump gain, inside a 1 % deadband, saturating at the bounds and continuing (it never halts the motor on error). The accumulated power is the last DAC written (pwr = DAC_HALT − dac), seeded to start_power on the first step after a (re)start. All arithmetic is 32-bit except a single 64-bit divide for the setpoint, so no libgcc 64-bit-division helper is linked. Each update:

target_ticks = us_to_ticks( pulse_count · target_ms_per_rev · 1000 / 5184 , period )  // one udiv64
err%         = sign(meas − target) · ( |meas − target| · 100 / target_ticks )    // 32-bit hardware divu
err%         = clamp( err%, ±op_p_max_err_pct )                  // saturate + continue (default ±25)
pwr          = first_update ? start_power : (DAC_HALT − dac)       // accumulated power, clamped to [min,max]
if |err%| > 1:  pwr += err% · step_per_pct                       // 1% deadband; err>0 = too slow = +power
pwr          = clamp( pwr, op_p_min_pwr, op_p_max_pwr )           // [64, 4095]
DAC          = 4095 − pwr

The step is proportional to the percent error and shrinks as speed approaches the setpoint, so the loop converges smoothly and self-limits with no integral term — structurally eliminating the integrator-windup limit cycle of the earlier incremental-µs law (BUG 1) and the heavier positional-PID arithmetic. The measurement is clamped to 4× target_ticks before the percent divide so the magnitude can never overflow 32-bit, and target_ticks is floored at 1 to guard the divide.

Per-pump gain (host-tunable, defaults baked in). step_per_pct is the proportional gain (“kp” — power units nudged per 1 % error), set separately per pump: ac_p_step_per_pct = 7, bp_p_step_per_pct = 6. Bench tuning found AC converges crisply at 7 (holds ±1 % at the operating power) while BP — with its more compliant peristaltic load — still oscillates at 7; it is stall-free and well-damped at 6, which holds 16 s/rev tighter than the earlier 3 (hall-interval mean 15.96 s/rev, motor_stop_events = 0; bench-validated 2026-06-15 against op ULP 1.3.2). Shared knobs (all CPU-writable shared variables; defaults compiled in so the binary regulates out-of-the-box): op_p_max_err_pct = 25 (error clamp), op_p_min_pwr = 64 / op_p_max_pwr = 4095 (power bounds), op_p_pulse_count = 16 (N), op_p_skip_max = 6 / op_p_skip_good = 4 (skip ladder), op_p_start_escalate_n = 3 (no-start escalation threshold). The legacy PID gains (kp/ki/kd_scaled) remain in memory for the dosing/parking PID and host compatibility (pinned with __attribute__((used, retain)) so --gc-sections keeps them).

Adaptive skip ladder (decimation) & hall-through-skip. Once settled the loop services progressively less often, to save power and avoid fidgeting on measurement noise. After op_p_skip_good consecutive in-band (|err%| ≤ 1) samples the ladder climbs one level (cap op_p_skip_max); a panic-sized error (|err%| ≥ op_p_max_err_pct) slams it to level 0. skip_for_level(L) = 2L holds the DAC for that many wake-ticks before the next measurement (level 6 ≈ one measurement every ~1.6 s at 16 s/rev). Hall-revolution counting runs on EVERY tick — including skipped ones — so revolutions are never lost during the idle; the AC path was corrected to read the hall switch before the skip early-return, matching the BP path.

Start, no-start, and stall interventions. The regulator preserves the production start + stall machinery and adds a no-start escalation. A stall is detected fast: sample_encoder() declares one when no encoder edge arrives at all within the short first-edge window (~50 ms), decoupled from the 16-edge measurement window. 5.5.1 ULP Cooperative Scheduler — Non-Blocking Continuous Loop (ULP 1.17.0)

As of ULP_Operational 1.17.0 (promoted 2026-07-26) the co-processor no longer executes the per-wake tick model of §5.5. The regulator is a single continuous, fully non-blocking cooperative loop: every state — AC_RUNNING, BP_RUNNING, dosing, dose coast, parking, park centre-offset and parking calibration — advances by exactly one encoder (plus hall) read per loop pass through a shared per-pass core, so no operation can own the ULP for longer than a few microseconds. The control law, the gains, the shared-variable semantics and the CPU-facing contract are unchanged; what changed is the execution model underneath them. The design was proven first on the TestOp dev track (dev.0.10–dev.0.13, owner-confirmed on the bench: calibration, park offset, dose, park and both pumps running) and then promoted into the shipping binary — a dev image validates the logic, but only the operational image validates the artifact, its stack headroom and its contract with the real firmware.

What blocked before. The 1.15.0 ULP was already a 1 ms cooperative dispatcher for steady-state regulation (set_wakeup_period(1000); each wake ran ac_tick() then bp_tick() and halted), but the blood pump’s special modes broke that model: one bp_tick() invocation spun internally for the whole operation — dose ~10 s, coast 5 s, park ≤30 s, parking calibration up to a 30 s sweep. Nothing else on the co-processor ran during those windows. The cooperative AC service of ULP 1.12.0 (SWR-271, §5.5) was a slice bolted inside the BP’s spin to paper over exactly this; the blocking windows are also where the deep call chains behind the stack-overflow class (GitHub #48) lived. The redesign removes the blocking window itself rather than each symptom.

Execution model (ULP 1.17.0). main() runs one continuous loop, servicing hall first and then both pump state machines on every pass, and returns to sleep only when nothing is measuring:

do {
    bp_hall_edge_service(bp_state == BP_RUNNING);  // count + timestamp EVERY pass, in EVERY state
    ac_tick();                                     // one per-pass step, never blocks
    bp_tick();                                     // one per-pass step, never blocks
    initialized++;                                 // per-pass liveness (the CPU's ULP-alive check)
    if (ulp_stack_canary clobbered) { latch; break; }
} while (!sched_idle());                           // sleep ONE wake period only when nothing is measuring

The per-pass drive core (seg_pass). One generic primitive serves every moving state, bound to each pump by thin bp_drive_pass/ac_drive_pass wrappers. It reads the encoder once; on a rising edge it accumulates a Simple-P segment of op_p_pulse_count = 16 intervals and, when the segment closes, applies the unchanged run_simple_p() law (§5.5) and writes the DAC. Because the loop polls at roughly 20 kHz — orders of magnitude faster than encoder edges arrive at operating speed — edge counting is gap-free and every MoveTo target is crossed exactly, where the old bounded windows both left inter-window gaps and could overshoot. Stall detection is unchanged in meaning: seg_stalled() reports no encoder edge within the SPR-scaled first-edge window (§5.5, ~50 ms floor).

The spin-up kick is per-pass as well (try_kick_pass). The load-bearing adaptive kick that breaks the sealed dead-point free (SWR-132, ULP 1.9.0 “the kick holds the drive”) keeps its exact behaviour — drive at bp_dac_start, and every ~50 ms without a first edge escalate the start power (persisted) while the motor stays energized — but the 50 ms wait is now spread across loop passes instead of a blocking sample. With no caller left, the linker reclaims try_kick_start() and sample_encoder(): the ULP blocks nowhere.

Skip ladder as a wall-clock deadline, and sched_idle(). The adaptive skip ladder of §5.5 is preserved — a purely continuous loop would spin the CPU whenever a pump ran, a real battery regression. In folded AC_RUNNING/BP_RUNNING, after each closed Simple-P segment the encoder is held off for the ladder interval expressed as a wall-clock deadline (*_skip_hold_until), not a pass count: a count would blow through while the other pump keeps the loop spinning. sched_idle() returns true — sleep one wake period — whenever every active pump is idle or inside a skip-hold or a recovery hold, and false only while a pump is actively measuring. The loop therefore bursts fast to catch its N edges, then sleeps through the hold, restoring the pre-fold power cadence; hall is still serviced on every wake. Dosing, park and calibration never skip, so they stay edge-exact.

Hall serviced at the top of every pass, in every state (SWR-289 strict). bp_hall_edge_service() is hoisted to the loop top and called once per pass regardless of state, so the ULP-owned crossing ring — and therefore the CPU’s length-7 deque (§5.6.3) — is updated on every hall tick, including crossings that occur during dosing, coast, park-offset and calibration. Counting is unconditional; the CPU wake stays gated to BP_RUNNING (the §5.5 / issue #46 semantics of 1.15.0). Because hall also runs on the ~1 ms sleep wakes, it is never blind for longer than one wake period. On the bench a dose longer than one revolution ticked bp_hall_revolutions 0→1 while bp_state was BP_DOSING — a crossing the tick model would have missed.

Mid-run stall recovery is non-blocking (seg_recover). A running-stall still power-cycles the DAC7574 driver — DAC→HALT, motor and encoder off — to clear the driver latch that an immediate re-drive cannot (the “BP dead after crash” fault class), but the MOTOR_RESTART_PAUSE_US (200 ms) settle is now a deadline (seg_t.recover_until) rather than a blocking pause. Only the recovering pump’s own drive is held off. The loop keeps running: ac_tick() and bp_tick() are still called every pass and hall is still serviced at the loop top, so if the other pump is measuring it is serviced with zero added latency, and if nothing else has work the loop sleeps one wake period at a time and re-services both pumps on every wake. This is strictly better than 1.15.0, whose regulate_pump() sat in a genuinely blocking 200 ms delay with the other pump unserviced throughout. Dosing and park keep the immediate re-kick, matching 1.15.0 (only RUNNING power-cycled).

Parking calibration — the firmware contract is UNCHANGED. Calibration is now the non-blocking BP_PARK_CAL state, but it answers the firmware’s existing protocol directly and no firmware change was required: _state_calibration writes test_request = TEST_DETERMINE_PARKING and polls for TEST_NONE; BP_IDLE enters BP_PARK_CAL on that request (or on the Control app’s bp_park_calibrating flag — both triggers converge on one flag so the exit paths stay single-path), and every exit — cancel, 30 s deadline, success, sweep-fail — clears test_request = TEST_NONE. That clear is required twice over: it is the firmware’s completion signal, and leaving it set would re-trigger calibration from BP_IDLE on the very next pass. Published results are unchanged: bp_hall_bracket_ticks, bp_park_offset_ticks = bracket/2 (SWR-119/120) and bp_park_enc_total. Gap-free per-pass polling also removes the inter-window encoder-edge undercount at its source — measured bp_park_enc_total = 5184 against PULSES_PER_REV 5184, where the windowed sweep read 5098–5111.

Implementation rule — do not write the DAC every pass. A ULP I²C DAC write costs ~1 ms, so writing it on every pass throttles the loop below the encoder edge rate and grossly undercounts (first calibration run: 1288 edges instead of 5184, at only 485 passes/s). The DAC latches, so it is written only when the commanded value changes: seg_pass() writes on a segment close (~1 in 16 edges), the kick writes at arm and on each escalation, calibration writes PARK_CAL_DAC once, and AC_IDLE/BP_IDLE skip the redundant per-pass HALT once stopped. This is a standing constraint for any future work inside the continuous loop.

5.6 Hall-Wake Session Architecture

The session loop uses hall-tick-driven Light Sleep: the main CPU sleeps indefinitely, waking when the ULP fires wakeup_main_cpu(). The ULP wakes the CPU on each blood-pump hall revolution, on each AC-pump hall revolution (ac_hall_revolutions), AND on a motor stop/stall event (motor_stop_events) — not BP-only as earlier revisions implied. CPU draws ~2 mA sleeping, wakes for ~1–5 ms housekeeping. (During DOSING the loop uses a plain asyncio 50 ms tick, not Light Sleep.)

Wake handler (_on_hall_tick)

On each wake:

1. Error check — read motor_stop_events; log warning if non-zero, clear flag.

2. Deque update — read bp_hall_revolutions, compute new revolutions, append external RTC timestamp to _blood_pump_sample_history (deque length 7). Proves blood from catheter tip at scheduled time has traveled 7 pump revolutions to dosing point.

3. Counter update — increment blood_pump_revolutions for telemetry.

4. External RTC verification — every 10 revolutions, log MCP79410 RTC read confirmation (IC6, I²C 0x6F, 32.768 kHz crystal Y2, ±2 ppm).

Beyond these BP steps, _on_hall_tick also reads + accumulates the AC-pump revolution counter (ac_pump_revolutions) with AC SPR diagnostics, and logs a per-wake “Hall tick” entry.

Session loop pseudocode

sub = IDLE
while True:
    _on_hall_tick()                              # ALWAYS serviced
    if sub != DOSING: sync_on_new_revolution()

    if sub == IDLE:
        if remaining ≤ 5 min: sub = TRIGGER   # wake up
    elif sub == TRIGGER:

    await sleep(500 ms if sub != DOSING else 50 ms)

The deque stores RTC timestamps of hall-switch events (one per revolution). When all 7 entries post-date the scheduled sample time, the pump has completed at least 7 full revolutions since that time. 5.6.1 Light-Sleep State Map (Power Management — SWR-243..250)

Light Sleep is gated by a phase rule: the firmware enters machine.lightsleep() only once the device has reached the SESSION state (state number ≥ _STATE_SESSION = 10). Every pre-session state performs its waits as plain asyncio sleeps — keeping the radio and the event loop alive so an operator/hub command is serviced within the ~1 s poll interval, and so no sleeper can run while an actuator is being driven. From SESSION onward the organizing structure is the blood-pump flush cycle (SWR-243): between samples the BP runs 2 minutes at 16 SPR, then parks at the sealed dead-point and rests 8 minutes, repeating — and it CONTINUES in FINISH so the line stays flushed after the last sample (SWR-248). The CPU light-sleeps in every phase except active dosing and fault handling (SWR-245); when the pump is turning the ULP wakes it on each hall edge just to update the length-7 deque (SWR-247), then it sleeps again. Single-owner backstop light-sleep

At most one task sleeps the CPU at any time, via one helper idle_lightsleep(backstop) → machine.lightsleep(LIGHTSLEEP_BACKSTOP_MS) (default 60 s, board_config-tunable, reset each nap). The two sleepers are mutually exclusive by construction: the flush cycle owns the nap through its RUN and REST phases (SESSION IDLE and FINISH), and the session loop owns it during preload/loading (TRIGGER) — which only exists while the flush cycle is suspended. There is no scheduler, no election, no registration — the earlier timed-election coordinator was removed entirely after it hung the CALIBRATION state (see the regression note). The ULP wakes the CPU EARLY on any hall revolution, motor stall, or failed start (wakeup_main_cpu → RTC_CNTL_SW_CPU_INT); the backstop is the RTC-timer liveness bound if no event fires. After every nap the sleeper yields _LIGHTSLEEP_SETTLE_MS (50 ms) so any frozen concurrent task runs one iteration before it sleeps again. A fault report in flight, or a pending start-FAIL confirmation, sets inhibit_lightsleep_until_ms and the sleeper degrades to short asyncio naps so those timers are not stretched.

Other tasks never sleep the CPU

Telemetry, the AC pump cycle, and the session / FINISH loops (outside TRIGGER) use plain asyncio.sleep_ms and never call machine.lightsleep — they simply ride along frozen during a nap and resume on wake. The AC pump keeps regulating on the ULP throughout every nap (bench-verified: AC holds SPR through the flush cycle). DOSING (SESSION sub-state 2) stays awake on a 50 ms asyncio tick — the CPU never sleeps while actively dosing.

Batched hub sync (SWR-246)

In-session hub sync is batched, not per revolution: the flush cycle syncs at each RUN boundary (_synchronize_from_blood_pump_cycle opens a fresh station, so an association dropped by the REST nap is re-established), the session loop syncs before and after each dose (_sync re-associates if needed), and faults push immediately through their own bounded station (SWR-236/249). The hub therefore updates roughly every 2-minute RUN plus at each dose and on errors; events that cannot be delivered at a sync point stay committed to flash and ship at the next one. The radio is fully down through the 8-minute REST — the association is deliberately not preserved across naps.

Real-time correctness across a nap

Because machine.lightsleep freezes time.ticks_ms (but not the external RTC), every deadline that must survive a nap is measured on the RTC: the sample schedule (_next_sample_ms), the FINISH 10-minute heartbeat, and the blood-pump idle window all use _rtc_time_ms(). The length-7 loading deque is count-based — _on_hall_tick appends one RTC timestamp per revolution and TRIGGER→DOSING fires when 7 revolutions post-date the sample time — so it is robust to how coarsely the CPU wakes.

ULP faults wake for logging

The ULP raises a CPU wake (wakeup_main_cpu()) not only on each hall revolution but also on a motor stall (MOTOR_STOP_AC/MOTOR_STOP_BP) and a failed start (MOTOR_START_FAIL_AC/MOTOR_START_FAIL_BP), ORed into motor_stop_events. On every wake the owner's first housekeeping step (_on_hall_tick → _drain_motor_stop_events) reads-and-clears the bitmask, decodes it, and writes a warning/log event with both pumps' drive + SPR (SWR-236). A fault is therefore logged promptly — near-instant if the fault interrupt cuts the nap short (OI-12), and at most one backstop (60 s) otherwise. Faults are never lost to sleep. A wake-side log marker (“Woke from lightsleep”) follows every nap, so a CPU wedged inside machine.lightsleep shows an “Entering…” with no matching “Woke…”.

Terminology

asyncio.sleep_ms(n) is the stock MicroPython cooperative sleep: it yields the current coroutine for n ms while the event loop keeps running other tasks — the CPU stays fully awake, no power saving. Used everywhere except the owner's nap: DOSING, the worker tasks, and every pre-session poll.

idle_lightsleep(backstop) is the firmware's sleeper helper: it powers the CPU down with machine.lightsleep(backstop) so the whole device (CPU + event loop) stops until the ULP wakes it or the backstop timer elapses. Its only callers are the flush cycle (RUN + REST) and the session loop's TRIGGER branch.

“Untimed + backstop”. The nap is conceptually untimed — it is meant to end when a real event (hall / stall / fail) fires the ULP wake — but it is bounded by the backstop (60 s) as liveness insurance so a missed wake can never hang the device: it wakes at least once per backstop, re-checks everything on the RTC, and sleeps again. This restores the §5.6 model (untimed, ULP-woken) with a safety timer, replacing the rejected timed-election coordinator.

Regression note. An earlier fw 0.1.80 build used a multi-sleeper timed election and routed pre-session telemetry/command-poll waits through it, which made the election run in the CALIBRATION state where it had never run before, stalled the calibration loop, and left the tape reel energized (it ran continuously). That model was rejected. Option A removes the election entirely and only sleeps the CPU from the main loop at state ≥ SESSION, so no pre-session phase can sleep or run a shared coordinator — the invariant the incident violated.

Wake-source / power reconciliation (OI-12 — largely confirmed). Bench 2026-07-07: the flush REST window measures ~20 mA with the CPU light-sleeping while the ULP keeps regulating the AC pump; the ULP wake from machine.lightsleep is confirmed (hall-tick deque updates and immediate stall/fail reporting through naps). Remaining: PPK2 profile of the RUN phase and the preload window under fw 0.1.86 (both now sleep between hall ticks), and a full-session energy figure. See §8.1 OI-12.

5.6.2 Session Recovery (Power-Loss Resume)

A power loss during a session MUST NOT lose the session. The device persists its session state to flash and, on every boot, resumes where it left off — guarded (fw 0.1.92/0.1.93, SWR-257/258) so that a resume can never run blind on a dead pump controller or pump blood without anticoagulant.

Persisted state

/state.dat — device state number, current sample index, session start time, blood-pump and AC-pump revolution counters, and the acquired hub’s SSID/BSSID. Written on every persisted-state change (session start, sample advance, FINISH entry). /time-table.dat — the sample schedule, written when settings are received from the hub. Deleting both files (the Control app’s Session Reset, SWR-317) is the sanctioned way to abandon a session: the next boot then initializes clean into AWAIT_CALIBRATION.

Boot algorithm (_state_initial)

1. Valve close (2 s cap, best-effort) — a crashed session may have left it open.
2. Restore /time-table.dat and /state.dat. Either missing or unreadable → clean initialization → AWAIT_CALIBRATION.
3. If the saved state is SESSION or FINISH: best-effort hub reconnect — ONE attempt to associate to the saved SSID/BSSID, NTP (accepted only inside the SWR-256 plausibility window), event upload and command fetch. Any failure is logged and the session resumes OFFLINE (it syncs at the next planned connect) — recovery is never blocked by the network.
4. ULP health verify (SWR-250/257): stack-overflow canary clear AND the core loop ADVANCING. On failure an error naming the required POWER-CYCLE is reported, the session is NOT resumed, and the device falls back to AWAIT_CALIBRATION — hub-visible, commandable, pumps off. This is underpinned at a lower level by the ULP start gate itself (SWR-257): the loader zeroes the INITIALIZED counter BEFORE starting the core and requires it to advance (≥ 2 invocations) — the random RTC-memory noise a power cut leaves behind cannot fake a started ULP (the pre-0.1.92 nonzero-read check could be, and was, fooled). One reload retry, then a hard failure.
5. Restore counters and schedule position (sample index + session start time). Resume does not consume a sample.
6. Start the AC pump cycle, followed by one explicit scheduler yield so its enable executes before the state machine moves (SWR-258). The session-entry path below runs synchronously into the blocking machine.lightsleep; without the yield a freshly-created task would not run until the first wake — the pre-0.1.93 defect that let the blood pump run 20–60 s without anticoagulant on resume.
7. Enter SESSION (or FINISH if the saved state was FINISH — the flush cycle continues per SWR-248; the session loop is not entered).

Session entry on resume

If the next sample is inside the 5-minute preload window (after a mid-session power cut it is typically overdue), the session takes ownership of the blood pump BEFORE the entry sync (SWR-244) — a slow hub cannot delay the preload. Independently, EVERY blood-pump start enforces the AC-first invariant (SWR-258) at the ULP register level: in any state ≥ SESSION, if the AC pump is not running it is started first (same SPR/preset/enable sequence the AC cycle uses) and a warning event is reported — on a healthy resume this guard stays silent; its warning appearing in the hub log means the primary ordering failed and should be investigated. The guard is inert below SESSION, so CALIBRATION and the priming states keep their designed dry/manual AC behaviour.

Operational note (bench, 2026-07-08). A session that has been recovered many times carries its ORIGINAL start time; once wall-clock time passes multiple schedule slots, every elapsed sample is overdue at once and the device processes the backlog back-to-back — rapid load/dose/park cycling that presents as continuous short tape/valve moves. This is the schedule catching up, not a fault; for bench work prefer a Session Reset and a fresh session over repeated recoveries of a stale one.

5.6.3 Hall-Deque Integrity — Registration Proof & Crossing-Time Stamps (fw 0.1.130/0.1.131)

What the deque is: the ULP timestamps every BP hall crossing (in EVERY state, SWR-289) into a 9-slot ring; the CPU consumes the ring into a 7-deep deque of crossing times. sampled_at semantics: the deque stamp marks when the blood now at the tape valve entered the catheter at the tip; it then transits the line for 7 BP revolutions before reaching the tape (the §5.7 load gate: dose only when the oldest of the last 7 crossings is at/after the scheduled time AND has advanced past the previous sample’s anchor — so backlog drains at one sample per revolution plus the ~50 s dose choreography, and every spot carries post-schedule blood).

Registration is proven complete (owner-requested audit, 2026-07-23): the overlay tunable DEQUE_AUDIT (board_overrides.json, default 0) makes the consume path emit one event per deque entry plus a per-batch completeness line (ring head vs ULP revolution counter vs CPU consumed total vs deque length) and an always-on warning when the 9-slot ring overflows. Live verdict across two sessions and 7 reboots: 120/120 and 70/70 crossings accounted, every contiguous segment exact, zero ring overflows — no hall tick is ever lost by the ring→deque→counter chain, including across WDT-reset recovery.

Crossing-time stamps are trustworthy since fw 0.1.131 (issue #51 — the audit caught three corruption modes live and all three are closed): (1) wrap clamp — the ULP publishes now_ticks once per tick and the publish goes stale through its busy windows (dose/park up to 30 s), so a crossing could read NEWER than “now” and the unsigned subtraction wrapped to a stamp 2³²/rate ms in the past (observed: exactly 105,703,256 ms = 2³²/40.617); a half-range test now stamps such entries at poll time (error bounded by publish staleness, seconds not hours). (2) rate hygiene — the tick-rate self-calibration runs AFTER the batch, is skipped (and its reference reset) when the batch clamped, and accepts only 110–170 ticks/ms (RC_SLOW nominal 136 ±25%; the stale-pair regime produced 40.6/69.2 undershoots and a 201.5 overshoot echo). (3) seed — the rate initialises at the 136 ticks/ms nominal so the first batch after boot/recovery back-dates within clock tolerance instead of stamping “now”. Acceptance (2026-07-23, 6 segments / 5 reboots): 0 negative deltas, 0 far-past stamps, all rates in-band, 5 wraps fired and all 5 neutralized. Residual accuracy: stamps are good to ≤ publish staleness (seconds) — adequate for the minutes-scale decisions built on them.

Reboot cost: recovery clears the CPU-side deque (stamps are RAM), so the first sample after every reboot pays a full 7-revolution refill (~96 s at 16 SPR) before dosing — deliberately conservative (re-establishes the post-schedule guarantee). Between reboots, consecutive backlog samples dose with ZERO fresh-revolution wait (proven live: loaded 7/7 in the same second, 8 s after the previous sample completed).

5.6.4 Warm-Boot Attach — Zero-Outage In-Session Reboots (GitHub #60; SWR-319/320/321/322/323)

Owner safety requirement (2026-07-28): the AC pump must pump 100% of the session — an in-session reboot must NOT stop it (blood-clotting risk, not a battery concern); and a WDT fire caused by a busy-but-alive task is better waited out than allowed to break the pump cycle. Delivered the same day in two prongs, accepted through nine bench runs (testlog 2026-07-28-007…-010) and DEFAULT-ON since fw 0.1.155.

Prong 1 — wait out the busy task: the in-session machine.WDT timeout is 180 s (SWR-215, owner-unlocked/relocked 2026-07-28; was 30 s), so a long flash+WiFi burst no longer converts into a reset.

Prong 2 — attach, don’t restart. The RTC domain, the ULP RISC-V core, the DAC7574 latch and the RTC-owned pump pads all survive a warm CPU reset — the historical outage was our own boot sequence. On a warm reset (HARD=2 or WDT=3) with a live session recorded in the validated bootstat RTC block (MAGIC 0xB5000001 @ 0x50001FF0, session-live sentinel 0x5E551011 @ 0x50001FFC; masked 32-bit compares), the firmware ADOPTS the running co-processor instead of reloading it (SWR-319): stack canary intact, no overflow latch, loop advancing within 120 ms, version family matching the on-flash map — any doubt falls through to the full SWR-257 restart. PWRON/brownout NEVER attaches (RTC memory is noise; the DAC7574 POR value is zero-scale = FULL POWER, SWR-276). /attach_off on littlefs is the operator kill switch.

The boot chain is gated end-to-end (SWR-321): littlefs /boot.py and /main.py skip the pump-pad claim and the pump-DAC HALT on warm+session-live boots (valve 8 and tape 41 are always safed; every other boot runs the full SWR-276 safe-off). Runs 6–8 proved the entire historical pad claim was these two Python files — with both gated, the pads’ RTC MUX_SEL stays intact through the whole boot and the ULP drives the pumps continuously across the reset. Standing lesson: /boot.py and /main.py are separately-deliverable littlefs units that a firmware.bin flash does NOT update (the littlefs copy shadows the image’s frozen copy).

Attach heal (SWR-320), the live-proven order: the warm boot’s C-runtime resets the RTC-I2C engine configuration, so an adopted ULP’s DAC writes would die silently (kick ladders escalate the register while the motors ride the DAC latch — the run-3/4 “encoder-blind” residue, root-caused live on the wedged board, testlog -007). The attach therefore: (1) re-asserts the SENS pad-register clock FIRST (defend_pad_clock(), #48 — a gated clock even freezes RTC_GPIO_IN reads, which misjudged spinning pumps as stopped in run 9); (2) motion-checks each pump by raw encoder-input toggles (250 ms/pump); (3) pauses ONLY running-but-motionless pumps (150 ms quiesce); (4) emits an I²C bus STOP with no register write (the DAC latch survives; safe-off is forbidden here); (5) re-initialises the RTC-I2C engine; (6) re-owns the pads (gpio_initialized=0 → the fold re-runs gpio_init_all(): slave address + dummy transaction on the fresh engine); (7) resumes the paused pumps through their kick path. A motion-PROVEN turning pump crosses the attach completely untouched — no stop, no kick, no surge — and its boot-window artifacts are cleaned (learned start power reset to the board_config baseline; that pump’s latched stall/start-FAIL bits cleared before the first drain, fw 0.1.156). Accepted residue: ONE self-recovered BP stall (flags=2) informational event per attach (the ~16 s batch window straddles the blind period; a delayed second clear could mask real stalls and is deliberately not done).

What survives an attach: pump drive state and learned kick powers; the SWR-318 hall ring (head monotone across the reset, newest ≤9 stamps recovered into the deque); and the session statistics — StateStruct v1 persists the consumption cursors with the totals and the AC delta baseline is monotonic-keep (SWR-323, GitHub #62), so the BP count no longer inflates by ring replay and the AC count keeps its REST-phase revolutions (the AC cycle is CONTINUOUS but dual-SPR by design: medium 20 s/rev while the BP is active, slow SPR during REST). Related hardening: every dose-path sync runs under a 45 s hard bound — on overrun the sync is cancelled and THE DOSE PROCEEDS (SWR-322, GitHub #61 mitigation).

Acceptance record: zero-outage accepted on fw 0.1.152 (testlog -008: two injected warm resets mid-session, AC revolutions +6/124 s at the 20 s/rev target, ring head monotone 11→18, 3/3 samples to FINISH); both-files-gated proof on runs 6–8 (-009, MUX_SEL intact); multi-attach soak on fw 0.1.154 (-010: three hub restart_device injections incl. one into FINISH, per-pump motion granularity “AC turning, BP off”, 6/6 samples, statistics tracking BP=62/AC=54); ladder-artifact validation on fw 0.1.156 (zero start-power-raise events, zero flags=15 bursts). SWR-324 — every network await bounded, scheduled loading deadlined (fw 0.1.157). SWR-325 — overdue-sample CATCH-UP on resume (owner decision). 5.7.3 Flush Cycle (Pre-Session Background Task)

Before the SESSION state begins sampling, the blood pump runs a repeating 2+8 flush cycle to keep the catheter clear. The cycle is managed by _run_blood_pump_cycle() and reported as three sub-states: ACTIVE, IDLE, SUSPENDED.

1. ACTIVE (2 min) — ULP regulates the blood pump at 16 s/rev. Simple-P regulation runs continuously (see §5.5).

2. Park — At the end of the active phase, the pump is parked at the hall home position (flush-cycle wall-clock backstop 34 s — _park_deadline in _run_blood_pump_cycle; the prior “480 s” was incorrect for this flush-cycle park, which is distinct from the dose-sequence park timeout).

3. IDLE (8 min) — Pump disabled. Hub sync performed at start and end of idle window.

4. Loop — Returns to step 1.

When SESSION enters the sampling loop, the flush cycle task is cancelled and its state set to SUSPENDED. The ULP runs the pump continuously from that point on.

5.7.4 Unified Session Loop (STATE 10: SESSION)

On entry, the firmware:

1. Cancels the flush cycle task (if active).

2. Enables the blood pump via ULP at 16 s/rev. The pump now runs continuously — no 2+8 cycling.

3. Registers the hall-switch interrupt handler (_on_hall_tick).

4. Enters a single polling loop with three sub-states: IDLE (0), TRIGGER (1), DOSING (2).

Each iteration (500 ms cadence in IDLE/TRIGGER, 50 ms in DOSING):

• Always calls _on_hall_tick() — reads ULP revolution counter, appends RTC timestamps to the deque.

• Outside DOSING: syncs with hub on every new hall revolution.

• Sub-state dispatch:

IDLE (sub 0) — Waits for scheduled sample time. When remaining_ms ≤ 5 minutes, transitions to TRIGGER.

TRIGGER (sub 1) — Waits for 7-revolution deque confirmation. Once the oldest deque entry post-dates the scheduled time, 7 full revolutions of fresh catheter blood have reached the nozzle (~112 s at 16 s/rev). Transitions to DOSING.

DOSING (sub 2) — Executes _dosing_tick(ctx) (see §5.7.5). When all doses for the current sample complete, advances the time table. If more samples remain, returns to IDLE. Otherwise transitions to FINISH (state 12).

5.7.5 Dose Collection — _dosing_init() + _dosing_tick(ctx)

Each dose is initialised by _dosing_init() which returns a context dict, then driven by _dosing_tick(ctx) called once per 50 ms loop iteration. The tick function returns _DOSE_CONTINUE or _DOSE_DONE.

5.7.7 ULP Integration — Park and Dose

Parking (bp_parking / bp_parked):

1. CPU writes bp_parking = 1 in RTC shared memory.

2. ULP enters BP_PARKING state. Motor drives toward hall switch at PID-regulated speed.

3. On hall activation (GPIO LOW), ULP counts bp_park_offset_ticks additional encoder edges to centre the rotor in the hall-active zone.

4. ULP clears bp_parking and sets bp_parked = 1 (success) or bp_parked = 0 (failure). Failure is detected by encoder rotation, not wall-clock time: the ULP accumulates encoder ticks into bp_park_enc_total and declares a timeout once it has turned a full revolution (PARK_ENC_TICK_LIMIT = 5200 ticks ≈ 1 rev) without the hall switch firing. A 30 s hard wall-clock backstop (PARK_SAFETY_TIMEOUT_US) guards against a stalled motor that produces no ticks, and the post-hall offset coast uses a 5 s backstop (PARK_OFFSET_SAFETY_US). This replaces the previous fixed 25 s PARK_TIMEOUT_US, which could report success even when the motor never started. bp_park_enc_total is exposed to the CPU so calibration can distinguish “motor did not start” (0 ticks) from “hall switch not detected” (≥ 5200 ticks, motor confirmed turning).

5. State machine polls bp_parking each 50 ms tick until cleared.

Dosing (bp_dosing / bp_dose_target / bp_dose_actual):

1. CPU writes target encoder pulses to bp_dose_target and sets bp_dosing = 1.

2. ULP enters BP_DOSING state. Counts encoder edges at PID-regulated speed.

3. When target reached, ULP transitions to BP_DOSE_COAST (1 s capture window for overshoot).

4. ULP clears bp_dosing, writes actual count (incl. coast overshoot) to bp_dose_actual, returns to BP_IDLE.

5. State machine polls bp_dosing each 50 ms tick until cleared.

Watchdog model (SWR-215, rewritten 2026-07-10; supersedes the earlier “no watchdog” stance): machine.WDT(30 s) is armed once a session exists (fed by a 1 s asyncio task) so an event-loop stall becomes a reset that RESUMES the session (SWR-257/259); pre-session states run under a lenient 120 s run()-wide floor (_WDT_PRESESSION_TIMEOUT_MS) because the suspend+DTR CDC freeze is invisible to the serial sink’s latch. Bench REPL work MUST call park_wdt() first — interrupting the firmware kills the feeder and the pending reset otherwise drops the serial port mid-transfer (the recurring “Device not configured” deploy failure, root-caused 2026-07-23). The old “WDT reset is a false recovery for a latched DAC7574” concern is superseded by the crash-boot recovery in pump_regulator.start() (I2C bus recover + DAC safe-off on every non-PWRON boot). Non-blocking serial (SWR-235, rewritten 2026-07-10): ALL console writes route through serial_sink (measure-and-latch): each write is timed and the FIRST slow one (≥200 ms) trips a one-way latch — no further code path touches the CDC. Known hole (issue #53): in the host-suspended+DTR-latched regime the C-layer write NEVER RETURNS (mp_usbd_cdc_tx_strn not-connected loop has no timeout), which the sink cannot measure; the watchdog floor is the backstop, and the §7.5a boot-loop breaker below closes the loop-forever case.

ULP in-place self-recovery (fw 0.1.111, SWR-275): when the health gate finds the #36 stack canary tripped or the ULP core stuck, the firmware attempts ONE in-place recovery — unconditional I2C bus clear + DAC CH0/CH1 safe-off, BP direction re-set, fresh ULP binary load with a FULL .bss zero (clears the canary latch), SWR-257 liveness proof — then re-verifies; a power-cycle is demanded only if the recovery itself fails. Customer battery devices cannot be power-cycled. Live-proven on the bench (artificial canary trip → recovered, ULP intact). The loader also pattern-fills the top 640 B of the ULP stack gap; stack_low_water() reads the true deepest excursion (idle: 228 B; measured static worst chain: 480 B of 696 B headroom).

Actuator power-on safety (SWR-276, fw 0.1.112–0.1.114 + IMG-4): the DAC7574 powers up at zero-scale = FULL DRIVE in the inverted convention (power = 4095 − register), and the AC driver enable is biased ON board-side while GPIO9/17 both float at reset (S3 datasheet Table 2-1). Defense in depth, all commanding enables LOW + DAC HALT: (1) second-stage bootloader hook (bootloader_before_init, IMG-4) drives GPIO 9/17/8/41 LOW with pull-downs ~tens of ms after power-on; (2) boot.py at ~0.5 s (field-measured); (3) main.py repeats before the USB gate. Residual exposure = the mask-ROM window (~10–50 ms) — closable only by the hardware pull-down on the AC enable, queued for the next HW revision.

Clock-first boot ordering (SWR-295/296, issues #52/#53 — 2026-07-23): two live incidents established the clock discipline now in the registry. (1) A mid-session WDT recovery can resume BEFORE NTP completes; with the RTC at the year-2000 power-on epoch every scheduled sample reads +26 years away and the session silently flush-naps forever while event sync works (issue #52; the operator-visible symptom is “stalled updates”). SWR-295: a pre-build-epoch clock forces an immediate hub NTP sync with bounded awake-retry in EVERY state; recovery must not schedule against it and must error loudly at the retry bound. (2) The boot flow entered AWAIT_CALIBRATION before NTP, so operator-facing events carried 2000-01-01 stamps. SWR-296: WiFi first, then NTP inside the SWR-256 plausibility window, and only then the AWAIT_CALIBRATION transition / acquired report / command processing — only the Boot/INITIAL forensic chain may ever be pre-epoch. Firmware implementation of both is queued (registry DOC 1.90).

7.5a Boot-loop breaker, quiet-console latch & boot breadcrumbs (issue #53, fw 0.1.132–0.1.134): a WDT reset in a pre-session state has nothing to resume: if the underlying freeze recurs (battery + detached USB in the radio-hot acquire loop reproduced it every 1.5–4 min), the device loops forever. bootstat.py (top-level module) keeps a 6-byte protocol in RTC user memory (magic 0xB5; survives WDT/soft reset, clears on power loss): consecutive-WDT-boot streak, the previous boot’s final breadcrumb, and the live breadcrumb. Every Boot event carries crumb + wdt_streak. At streak ≥3 the breaker creates /console_quiet and serial_sink is born latched from then on (no code path touches the CDC; delete the file to restore prints; /serial_sink_off dev bypass still wins). Breadcrumb ids bracket every suspect call: 10 poll-loop top; 11/12 console write (a WDT boot reporting 11 died INSIDE a CDC write); 13/14 fast settings GET; 15/16 full event sync; 17/18 NTP; 19/20 scan; 21/22 connect; 23/24 command handling. Fork facts established en route: machine.reset() reads back as HARD (code 2), and RTC user memory is wiped by a full firmware boot (suspected overlap with the ULP’s reserved slow-mem at reload) — tolerated because the per-poll crumb rewrites re-establish the blob after every ULP load.

7.8 Flashing the Firmware Image (MicroPython)

The device firmware ships in three layers, each deployed by a different mechanism. Reflashing the MicroPython image is the heavyweight operation and is rarely needed — a normal application fix is a serial .py deploy, and a pump-controller change is a deploy_ulp.py run. Reflash the image only to change the MicroPython runtime itself or its sdkconfig (for example the watchdog / brownout settings baked into fw 0.1.98 below).

⚠ CRITICAL (issue #54, discovered 2026-07-23): the IMG-4 image (v1.25.0-12, 2026-07-16) freezes its own main.py, and the frozen copy runs INSTEAD of the filesystem /main.py — proven live: the firmware boots identically with /main.py renamed away. Every /main.py deploy since IMG-4 has been silently dead code (the deploy tooling checksum-verifies the file and reports success — a false-confidence loop). Until an image rebuild un-freezes it (IMG-5, one-change + boot-prove discipline), ALL early-boot code changes go in fluispotter/fluispotter.py module level (the earliest file proven to execute every boot; the fw 0.1.134 bootstat hook uses an idempotent guard so a future de-frozen image is safe). The “FS copies shadow the frozen ones” rule in the layer table holds for package modules — NOT for main.py itself on this fork.

Flashing. Download the release fluispotter-<tag>.bin, then, with the board in ROM download mode (below):

python3 -m esptool --chip esp32s3 --port <PORT> \
    --before no-reset --after hard-reset write-flash 0x0 fluispotter-<tag>.bin

The image is written at offset 0x0 (bootloader + partition table + app). This overwrites only the app region; the littlefs vfs partition at 0x200000 (6 MB) — which holds the loose fluispotter/*.py, the ULP binary, board_config/board_overrides.json and state.dat/time-table.dat — is preserved across the swap. esptool hash-verifies the write.

Entering ROM download mode (the S3 procedure — verified 2026-07-09). esptool cannot put the ESP32-S3 into download mode by itself over the native USB — its DTR/RTS reset gives Failed to connect: No serial data received, and repeated attempts wedge the running board. Use one of these instead:

  • Physical Boot1 button (the robust method — works even when the flashed image is broken and the REPL is dead). Boot1 is the GPIO0 boot-strapping button (§4.7 BOOT_MODE); this board has no reset/EN button. Sequence: power OFF → press and hold Boot1 → power ON while holding → keep holding ~5 s → release. The mask-ROM (independent of the flashed firmware) enters download mode and enumerates as the USB-Serial-JTAG device VID 0x303A / PID 0x1001, and the port stays up steady. (A port that flaps in and out instead means the app is boot-looping, not stable download mode — hold Boot1 through the whole power-on.)
  • machine.bootloader() from a live REPL — only if the app already boots and the REPL is reachable; reboots straight into ROM download mode.

This board has no auto-reset: esptool --after hard-reset pulses the RTS pin, which is not wired to EN here, so it does not restart the board. After a write-flash the board stays parked in download mode — you must hand power-cycle it (Boot1 released) to actually boot the freshly-flashed image. Read the USB PID to know the state: 0x1001 = ROM/download mode (esptool can talk); 0x303A:0x4001 = MicroPython native USB-CDC = the app is running (esptool cannot talk).

Full-image backup / restore. No flashable full image is kept in any release (the restore-fw0.1.78 release holds only the ULP .bin files). Before flashing, dump the whole 8 MB via the same download-mode entry (--before no-reset because the board is already in download mode):

python3 -m esptool --chip esp32s3 --port <PORT> \
    --before no-reset --after hard-reset read-flash 0x0 0x800000 backup.bin

Verify a good dump: first byte 0xE9 (ESP32 image magic); littlefs / MicroPython / fluispotter signatures present. Restore is an exact rollback (the dump includes the littlefs FS = the .py/ULP/config/state): write-flash 0x0 backup.bin.

A flashed image that will not boot — NOT a power or hardware problem. The failure signature — no INITIAL indicator-LED flash + the spot/line sensor LEDs stuck ON + no USB enumeration at all + no hub sync — means the flashed image itself does not boot (a bad/unvalidated runtime or sdkconfig). It is not inadequate supply and it is not a dead board (standing project rule: it is never the hardware). Do not diagnose this as a brownout or a weak/current-limited supply. Recovery is deterministic: force ROM download mode with Boot1 (above) and restore a known-good full-flash image, then hand power-cycle — the board comes straight back (proven 2026-07-09, when a rebuilt image would not boot and was rolled back). The specific reason a given build fails to boot is determined off the board from its image + build provenance (offline forensics on the .bin), never by swapping supplies.

Operational note — the PPK2 is not the board. When a Nordic Power Profiler (PPK2) is inline, it enumerates as a separate serial device: Nordic Semiconductor VID 0x1915, versus the board’s Espressif VID 0x303A. output/_serial_io.find_port VID-filters the PPK2 out, but esptool auto-detect does not — always pass an explicit --port. Never restart the PPK2 power-logger into a live DUT: restarting it resets the PPK2 and cuts the device’s power (a real interruption, unrelated to the image not booting).

7.9 Building a New Firmware Image — the Verified Method

This is the exact procedure executed and boot-proven on 2026-07-09 (images v0.1.99-base and v0.1.99, the interrupt-watchdog fix for issue #44). Every step below was performed at least once; nothing here is theoretical. It exists because its violation — delivering a config tweak by bumping the runtime submodule to the fork tip, which silently swapped the entire MicroPython runtime a dev-cycle forward — produced the non-booting v0.1.98.

Rules (standing): (1) one sdkconfig change per image, never stacked; (2) the runtime base is always an explicit, proven commit pin — never a branch tip; (3) every image passes the pre-flash gates before it touches the board and the boot-proof before it is trusted; (4) a restorable full-flash backup exists before flashing (§7.8).

Step

Action (as executed)

0. Backup

Confirm a verified full-flash backup of the current working image exists (§7.8 read-flash). This is the rollback for every step below.

1. Fork branch

In fluispotter/micropython, create a branch off the proven base commit (2026-07-09: fluispotter-v1.25-int-wdt-1000ms off 1d140090, the v1.25.0-esp32 tip the firmware repo already pinned) and add one commit containing the single sdkconfig.board change (the INT_WDT commit is 3c8d3909, +5/−0: four comment lines + CONFIG_ESP_INT_WDT_TIMEOUT_MS=1000). 3. CI build

Tag v* and push the branch + tag → build.yml builds (ESP32_GENERIC_S3 / SPIRAM_OCT, ~9 min) and publishes fluispotter-<tag>.bin as a Release asset.

4. Pre-flash gates

On the downloaded .bin, BEFORE it touches the board: Gate 1 — strings -a <bin> | grep 'MicroPython v1.' MUST report exactly the intended pin (e.g. v1.25.0-8.g3c8d3909), not an unintended runtime (this single gate would have stopped v0.1.98, which read v1.26.0-preview.151). 5. Flash

Enter ROM download mode with Boot1 (§7.8; PID 0x1001, esptool talks), then write-flash 0x0 <bin> (littlefs at 0x200000 preserved; esptool hash-verifies). The board stays in download mode afterwards — the RTS “hard reset” does nothing on this board.

6. Boot-proof

Plain power-cycle, Boot1 untouched. Acceptance = ALL of: the INITIAL (blue) LED at boot + USB re-enumerates as native CDC 0x303A:0x4001 + hub sync resumes. Only a fully boot-proven image is trusted; a held Boot1 lands back in 0x1001 download mode (harmless — power-cycle again without it).

7. Sequence

If the pipeline has never produced a bootable image from the intended base, build an Image 0 first: the base pin with zero config change (2026-07-09: v0.1.99-base at 1d140090, boot-proven), then the one-change image on top (v0.1.99 at 3c8d3909, boot-proven). A failure then attributes unambiguously: Image 0 fails → the base/pipeline; Image 1 fails → the single change.

8. Rollback

Any failure at step 6: Boot1 → download mode → write-flash 0x0 <backup> → plain power-cycle. Proven same-day (the v0.1.98 recovery).

Executed instances (both boot-proven 2026-07-09): v0.1.99-base — runtime v1.25.0-7.g1d140090, no config change, the pipeline-proof image. v0.1.99 — runtime v1.25.0-8.g3c8d3909, + CONFIG_ESP_INT_WDT_TIMEOUT_MS=1000 only: the delivered fix for the intermittent post-dose interrupt-watchdog reboots (issue #44). Brownout remains deferred as its own future image (it would only pin the existing esp-idf level-7 default).

Runtime sdkconfig changes are image-level and must be built + boot-proven ONE at a time. Changing the ESP-IDF sdkconfig (interrupt-watchdog, brownout, PSRAM, console, …) requires rebuilding the whole MicroPython image — it cannot be a loose .py deploy. The two intended safety changes are CONFIG_ESP_INT_WDT_TIMEOUT_MS=1000 (raises the interrupt-watchdog margin from the 300 ms default to 1000 ms — the fix for the intermittent post-dose “WDT code 3” reboots, the interrupt watchdog firing on a transient >300 ms interrupts-off window in the Wi-Fi / light-sleep path, GitHub issue #44) and enabling the brownout detector (CONFIG_ESP_BROWNOUT_DET).

Incident — v0.1.98 (2026-07-09) did NOT boot and was rolled back. A single fork rebuild bundled both sdkconfig changes on top of a year-newer MicroPython + esp-idf runtime, and the resulting image would not boot (no USB enumeration at all). It was recovered by restoring the known-good full-flash backup. Lessons now standing: (1) change one sdkconfig setting per image (interrupt-watchdog first; brownout — least critical — last), never stacked, so a boot failure is attributable; (2) every separately-deliverable unit (image/runtime, app, ULP) carries its own version + build provenance stamp; (3) a freshly built image is boot-proven on the bench (INITIAL LED + USB 0x4001 + hub sync) before it is trusted or endurance-tested. The interrupt-watchdog change was re-delivered under this discipline and boot-proven the same day (v0.1.99, step table above); brownout remains deferred.
