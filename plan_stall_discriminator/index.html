PLAN — Discriminating the BP stall class: real hesitation vs encoder blindness

Status: OPEN, board now FREE — field run 2 ended 2026-08-02 11:48 UTC on battery exhaustion (43/50 samples, 37.4 h, zero reboots). Board is dead/unpowered until the owner revives it; reset_session deliberately NOT queued (#65). Owns: GitHub #68 (detector sensitivity + seg_recover policy), touches #48 (encoder blindness). Origin: owner question 2026-08-02 — "can the stalls be attributed to the latest code changes? We ran 44 hours without a single stall event before this."

1. What is already settled (do not re-litigate)

  • The events are real, not a reporting artifact of the fold alone. Run 2026-07-28-011 (fw 0.1.156) and run 2026-07-31-003 (fw 0.1.161) ran the identical ULP dev.0.24 binary, same 53-min cadence, comparable duty (205 vs 187 BP starts). Run 011: 0 motor stops in 36 h. This run: 9. Same detector, different outcome.
  • The detector did get ~16× more sensitive across the fold (relevant only to the older 44 h baseline, ULP 1.12.0): the stall clock changed from a first-edge window (live ~6 % of a segment) to a free-running inter-edge watchdog (live 100 %). Timeout value unchanged at 50 ms. So a 50–400 ms hesitation that ULP 1.12.0 could not see is reported now. Never compare stall counts across the fold boundary.
  • All 7 BP stalls were bp_state_word = 1 (BP_RUNNING) — the inter-edge watchdog. Not the new BP_PARK_OFFSET site, not dose, not park.
  • seg_recover de-energizes and cold-restarts on that 50 ms window, which is what produces the 3 downstream BP start-FAILs.
  • RETRACTED (owner correction 2026-08-02): the "dead-point / position hard spot" explanation. On the devboard the parking position is NOT in a hard spot. That measurement came from the Test2 bench and must not be reused here. Any mechanical explanation now needs its own evidence.

1b. Evidence added 2026-08-02 — sample deltas are NOT a signal, and the hall path was healthy in every loading window

Owner hypothesis tested: "deltas of more than 3 seconds coincide with a flush cycle continuing into the 5-minute pre-sample flush." REFUTED — the condition never occurred. Pump state at preload, derived from the enable/disable events against each Waking up for sample, was PARKED at 42/42 samples with a determinable state (sample 0 indeterminate). Not one preload caught a running flush cycle. Structural reason: the flush cycle restarts after each sample (SWR-243, session IDLE branch), phase-locking it to the 53-min schedule — every preload landed 100–148 s into the 8-minute REST. Independent phases would have caught a RUN in roughly 20 % of samples; 0/42 is not chance.

What the deltas actually are: one-revolution phase quantisation. Loading requires 7 hall crossings AFTER scheduled_at and sampled_at is the first of them, so the delta is bounded by one revolution period and wraps. Measured across the run:

delta ≤ 3 s (n=34) delta > 3 s (n=9)
spin-up (preload → first crossing) 19.4 s 19.4 s
revolution period 16.0 s 16.0 s
crossings preload → loaded 25 26

Nothing physical differs. A +15 s delta means a crossing missed the scheduled instant by about one second, so the next arrives ~15 s later. Intermediate values (samples 5, 6, 11 at +3; 7 at +4; 8 at +5) show the phase creeping through the boundary rather than flipping. Consequence for this plan: delta is not evidence of pump health and must not be used as one — an earlier mid-run reading of the +15 s cluster as battery decline was wrong.

What this DOES contribute to hypothesis (b). Across 43 loading windows the inter-crossing intervals were a uniform 15–17 s with ZERO intervals ≥ 24 s — roughly 1,075 consecutive hall crossings with no dropped registration anywhere. So:

  • the hall registration path is demonstrably healthy in the TRIGGER / loading context (CPU awake, measuring every revolution), and
  • therefore any blindness is episodic, not systemic — it did not manifest once in ~1,075 crossings.

This does not refute (b): the stalls occurred in the flush-cycle BP_RUNNING context, which differs from loading (CPU mostly asleep between hall wakes, different duty). But it narrows the target and raises the value of Experiment 2 — the bench drive must reproduce the flush-RUN context specifically, not a loading-style continuous drive with the CPU attentive, or it will simply re-confirm the healthy path already measured here.

2. The two live hypotheses

(a) The rotor really hesitated

With the park not a hard spot, this needs its own evidence instead of being the default. The leading candidate in this branch is non-mechanical: supply sag from the CPU's flash-commit + Wi-Fi burst running concurrently with regulation — the mechanism the firmware review flagged, which also explains the self-reinforcing cluster (a stall wakes the CPU in ~1 ms, which does statvfs + a large event append + a flash commit + a radio push while the ULP executes its escalated re-kick; a failed re-kick emits another fault, which fires another burst). This is the SWR-265 collision class recreated at the fault-report path.

(b) The rotor kept turning and the ULP went blind

The #48 SENS_IOMUX_CLK_EN class, where RTC_GPIO reads freeze. A blind ULP on a perfectly healthy motor trips the same watchdog identically. Two things point this way that were under-weighted: - at the first stall the regulator was driving at a normal running power (3370 — not a struggling motor), and - every fault payload carries iomux14 = iomux18 = 0x00001a00 on the two encoder-enable pads.

Both are suggestive, not conclusive: the iomux value was originally dismissed because RTC MUX_SEL was still set (RTC override wins), and the same 0x00001a00 appears in an fw 0.1.143 payload never attributed to pad theft.

No pick between (a) and (b) without evidence.

3. The decisive experiment

Question: were encoder edges still accruing at the instant the stall was declared?

That single fact separates the hypotheses cleanly: - edges still accruing → the ULP was blind → (b) - genuinely no edges → the rotor stopped → (a)

Experiment 1 — edge-counter witness in the fault payload (preferred; cheap, permanent)

Record the ULP's encoder edge/interval counter (and the RTC tick of the last observed edge) at the moment seg_stalled() fires, and surface both in the existing FAULT payload alongside the fields already there.

  • Cost: a few words of ULP state + payload fields; no new machinery, no extra RTC maths.
  • Watch the ULP stack headroom gate (build_verify_ulp.py) — it is the binding constraint on any ULP change.
  • Value: works in the field, forever, on every future stall, without a bench rig.
  • Note the payload already carries gpio_in; a single sample of it is not a witness — the counter is.

Experiment 2 — bench drive with an independent rotation witness (confirmatory)

Drive the BP on the bench (board idle, USB attached, session not required) and check whether declared stalls coincide with an actual rotor stop, judged independently of the encoder path: hall-crossing counter and/or direct observation.

Reproduce the FLUSH-RUN context, not a loading-style drive (see §1b): the 2-min RUN / 8-min REST cycle with the CPU napping between hall wakes, repeated for hours. A continuous attentive drive would only re-measure the path already proven healthy across ~1,075 loading crossings, and would produce a false negative.

  • If stalls are declared while the hall counter keeps advancing → (b) confirmed outright, no ambiguity.
  • Pair with the #48 probe already in the tree (tools/ulp_probe/) to read SENS_IOMUX_CLK_EN at the moment of declaration.
  • Must include a must-fail control (a deliberately stalled rotor) so a "no stalls detected" result cannot be mistaken for a working test.

Experiment 3 — (a)-specific, only if Experiment 1/2 point at a real stop

Correlate stall timestamps against the CPU's flash+radio bursts, and A/B the burst by deferring the fault report away from the recovery kick (the #68 fix). If deferring the burst removes the cluster, (a)'s supply-sag mechanism is confirmed by intervention.

4. Decision rules and consequences

Outcome Verdict Consequence
Edges accruing at declaration (b) — spurious stall reports Escalates #68 from advisable to urgent: seg_recover is stopping healthy motors. Fix the detector (require a real edge-loss, not a blind read) AND the recovery policy. Re-open #48 scope: blindness reaches the operational path.
No edges, rotor stopped (a) — real hesitation Pursue the supply-sag mechanism; land the #68 burst-deferral (SWR-265 pattern, third instance) and re-measure. Mechanical remains unexplained and needs its own investigation — not hard-spot drag.
Mixed across events Both classes present Fix (b) first — it is the one that corrupts the evidence for (a).

Independent of outcome, already justified by #68: do not power-cycle a motor on a single 50 ms window. Require N consecutive stall windows, or first raise power on the energized motor (ULP 1.9.0 lesson: stiction only has to be overcome once) and power-cycle only if that fails.

5. Prerequisites and sequencing

  1. Field run 2 completes (~19:45 local 2026-08-02) and is concluded with reset_session. Do not touch the board before then.
  2. Remove /crumbs_on — armed during this run for the #67 hunt, it is a confound (2 RTC-RAM read-modify-writes per console line) that run 011 did not have. Any comparison run must be without it.
  3. Experiment 1 (ULP change) → build, headroom gate, deploy, boot-prove.
  4. Experiment 2 on the idle bench, with the must-fail control.
  5. Record on #68 with file:line + failure scenario; update SWR/HUBR text only once a branch is proven, per the fix-closure discipline.

6. Explicit non-goals

  • Do not re-run a 44-hour endurance test to chase this. The discriminator is a bench-minutes experiment, not an endurance question.
  • Do not quote historical stall counts across the fold boundary as a trend.
  • Do not attribute anything to mechanical drag at the park position on this board.
  • Do not use sample deltas as a health signal (§1b): they are one-revolution phase quantisation, identical spin-up and revolution period on both sides.
