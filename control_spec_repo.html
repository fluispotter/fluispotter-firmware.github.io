1. Document Overview


This document specifies the Fluispotter Control Application — a macOS PyQt6 desktop app used during development to actively drive and tune a connected Fluispotter device over USB serial. Unlike the passive Monitor app, the Control app injects MicroPython into the board's raw REPL to command pumps, the valve, the tape reel, LED rails, and the ULP regulator, and to run diagnostic test routines. This document describes its software structure, data handling, hardware interaction, and every tab.

It is a living document. Per the same discipline as the Device Specification Repository, every change MUST bump the version in the cover page and the Document Control table below, and add a row to the Change Log.

2. Purpose & Scope


The Control app is the active bench tool for the device. It does everything the Monitor app does (live telemetry display) and adds command and test capabilities: start/stop and tune both pumps, exercise the valve and tape motors, run the regulator tuner, characterise pumps (DAC sweep, resistance map, encoder fidelity), calibrate blood-pump parking, drive the sensor/LED rails, pull on-board logs/diagnostics, and manage a board asset registry.

Because it drives hardware, its design centres on a single shared serial link that is multiplexed between a default live-monitor stream and on-demand injected test scripts, with strict mode gating so two activities never fight over the board.

Scope: the macOS Control desktop app only (control/). Firmware, ULP, and the RPi hub are covered by the Device Specification Repository.

3.3 Threading Model

ThreadResponsibilities
GUI threadQt event loop, all widget updates, the 100 ms drain + 2000 ms health timers.
SerialBridge daemonOwns the pyserial port + raw-REPL reader loop; parses JSON; pushes dicts onto a queue.Queue(2000). Never touches Qt directly.
Inject workersFor blocking injects that involve a raw-REPL handshake or a binary swap on a possibly-wedged board (e.g. PID Tuner start/stop), _inject_async spawns a short-lived daemon thread and marshals any failure back to the UI via a _run_on_ui pyqtSignal — so the GUI never freezes.

Port access is serialised with _inject_lock; a _pause_reader event lets inject()/run_command() temporarily take the port from the reader (the caller sleeps ~0.3 s for an in-flight readline to drain). A custom sys.excepthook keeps the app alive if a slot raises.

3.4 Three ULP Binaries & Runtime Swap

The board carries three ULP binaries that the Control app swaps at runtime via injected snippets:

BinaryUse
pump_regulator.binOperational / default. The live production regulator; loaded at boot and after every test.
pump_test.binDiagnostic routines: resistance map, encoder fidelity, fixed-power run, DAC sweep.
pump_test2.binRegulator-only test harness for the PID Tuner's Test (kp/ki/kd) and Simple-P (16-tick) modes.

Diagnostic scripts swap in a test binary for the run and reload pump_regulator.bin afterward. The PID Tuner's Operational mode runs on the live binary with no swap.

4. Data Handling


4.1 Serial Transport — Raw-REPL Injection

SerialBridge speaks MicroPython raw REPL over pyserial using control bytes: Ctrl-C (0x03, interrupt — sent twice), Ctrl-A (0x01, enter raw REPL), Ctrl-D (0x04, execute). connect(port, script) opens the port, interrupts, enters raw REPL (waits for the banner, up to 5 s), and execs the script (UTF-8 + 0x04, written in 64-byte chunks). The reader loop then JSON-parses {...} lines into the queue; non-JSON (REPL echo/prompts) is dropped.

MethodBehaviour
inject(script)Stops the current script and runs a new one (interrupt → raw REPL → exec); updates _current_script.
run_command(code)Execs a one-liner, then re-execs _current_script without a second Ctrl-A (board stays in raw REPL). Used for live mem32 pokes (Pumps Start/Stop/Apply).
run_command_with_output(code, timeout)Execs + reads the raw-REPL stdout framing — used by the connect-time address probe.
disconnect()Clears _want_connected, sends Ctrl-C, closes the port.

On a USB drop, the reader keeps _want_connected and _try_reconnect re-opens (last port then find_port()) and re-injects _current_script.

4.2 board_script.py — Injected Scripts & Frame Namespaces

None of board_script.py runs on the Mac. Each factory returns a MicroPython source string that the app injects; the script runs on the board and prints JSON frames. The default stream is MONITOR_SCRIPT (the same telemetry the Monitor app reads, keys t, ac_*, bp_*, actuators, sensors). Test/command scripts emit namespaced frames so the router can dispatch them:

4.3 Address Resolution by Name + Connect-Time Guard

Every ULP shared-memory location is resolved by name from the auto-generated maps fluispotter/variables.py (_ULP, operational), test_variables.py (_ULP_TEST), and test2_variables.py (_ULP_TEST2), loaded standalone via importlib (with a micropython.const shim) so they import on desktop CPython. The resolved integers are embedded as literals at script-build time — never hardcoded hex — which eliminates the stale-address bug class on ULP rebuilds.

At connect, _verify_board_addresses() probes ULP_VERSION + INITIALIZED (twice) via run_command_with_output; if the loaded map doesn't match the running ULP (e.g. the app wasn't restarted after a deploy), it rejects the connection with a “restart the control app (stale addresses)” message.

4.4 Application Modes

MainWindow holds a _mode that gates routing and prevents two activities from fighting over the board. The default is _MODE_MONITOR (live telemetry). Starting a test sets the matching mode (e.g. _MODE_DAC_SWEEP, _MODE_PID_TUNER, _MODE_ENCODER, _MODE_PARK_CAL, _MODE_PARKING, _MODE_EVENT_LOG, _MODE_DIAGNOSTICS, _MODE_SENSORS); a terminating done/err frame re-injects MONITOR_SCRIPT and returns to monitor mode. Live pokes (Pumps Start/Stop/Apply) only run while in monitor mode.

4.5 Inbound Data Flow

board script print(json.dumps(d))  (USB-CDC)
   -> SerialBridge.run()   readline + json.loads
   -> bridge.queue         (queue.Queue, max 2000)
   -> _drain_queue         (QTimer 100 ms, up to 20 frames/tick)
   -> _handle_frame(data)  route by key + _mode

_handle_frame always logs the raw dict to the Log tab, then dispatches: err/done → the active panel's handler + re-inject MONITOR_SCRIPT; ev* → Event Log; diag* → Diagnostics; res_rev → Resistance Map; enc_rev/fp_* → Encoder; dac_step → DAC Sweep; pid_* → PID Tuner; sensor → Sensors; park_*/park_cal_* → Parking or Resistance Map (by mode). A normal telemetry frame (t + monitor mode) is pushed to Pumps and Valve-Tape; bp_bracket is forwarded to the Resistance Map and PID Tuner hall-arc helpers.

4.6 Outbound Data Flow (Command / Script Injection)

MainWindow slots build a script via a board_script factory (or an inline snippet) and call bridge.inject() (full script), run_command() (one-liner), or run_command_with_output() (probe). Stop paths typically write ULP RTC memory directly (e.g. mem32[TEST_REQUEST]=0, AC/BP_PUMP_RUNNING=0) then re-inject MONITOR_SCRIPT. The DAC/power convention is inverted throughout: scripts write DAC register = 4095 − power.

6. Tab Reference


Tabs are listed in display order. “Drives hardware” tabs are flagged; the rest are read-only.

6.1 Pumps

Drives both pumps. Purpose. Side-by-side live control + monitoring of the AC and Blood motors. Each card runs the motor in open-loop Power mode (fixed power, step_per_pct=0) or closed-loop SPR mode (operational Simple-P 16-tick regulation to a target seconds-per-rev).

Displays. Per pump, a Simple-P stats grid: state (●/○ + name), actual power (=4095−DAC), the true hall-interval SPR (wall-clock between hall-revolution increments, which averages out the peristaltic ripple in the encoder-batch sub-sample) + its error vs target, target SPR, skip-ladder level, hall switch, hall revolutions, motor-stop events, pulses/batch, measurements/s, and encoder duty % (Σ batch-µs / wall-second — not the inverse of skip level: at the 1 ms ULP wake even max skip leaves ~30–50% duty; row tooltips explain it); plus a dual scrolling chart (last 5 min + full history) of power + duty with hall-active shading, and a read-only readout of the Simple-P constants the card writes on Start.

Controls. Run-mode radio (Power/SPR); Power (0–4095); Target SPR; Start power; Apply SPR (live target change + re-assert step, no restart); Start; Stop. The legacy PID Kp/Ki/Kd gains were removed — Simple-P uses a fixed per-pump step_per_pct, not a tunable PID; arming no longer clobbers the BP dose/park PID's board_config boot gains. Data. Read via update(d) (MONITOR_SCRIPT keys incl. ac/bp_skip, ac/bp_revs, stop_ev); write via command_requested → inline mem32 snippet through run_command() (monitor mode only). Addresses by name from variables.py.

6.2 Resistance Map

Drives one pump. Purpose. A “climate-spiral” polar visualisation of per-segment rotational resistance: spins a pump at constant DAC power for N revolutions (PID disabled) and plots each revolution as a closed 32-point polygon whose radius is the µs timing of each encoder segment. The same tab doubles as the live BP parking display.

Displays. Viridis-graded per-rev polygons, Mean/Max/Min stat rings, adaptive reference circles, red-x timeout markers, a yellow hall-active rim arc (angle-locked map → host-sampled fraction → calibrated bracket), and a colorbar. Parking mode: a rotating needle + hall target line that turns green on success / red on timeout.

Controls. Pump; Revolutions; Power; Run; Stop; Park BP (BP-only). Data. resistance_map_script / park_pump_script frames routed in. Swaps in the test binary for the map run.

6.3 Encoder

Drives one pump. Purpose. Encoder-fidelity bench — turns a pump a fixed number of hall-gated revolutions and verifies each produces the expected 5184 ticks. A second “Fixed Power Run” section drives a pump at a raw DAC power for N revs while streaming live encoder/hall telemetry (spin-up / run-in characterisation).

Displays. A bar chart of measured ticks/rev colour-coded by deviation (green ≤1%, amber ≤5%, red otherwise) with a 5184 reference line and tolerance bands; a summary table (Revolution, Ticks, Δ, Error%); status labels for both sections.

Controls. Encoder test: Pump, Revolutions (1–20), Run, Stop. Fixed-Power: Pump, Power (0–4095), Revolutions (1–100), Run at power, Stop. Data. encoder_fidelity_script / fixed_power_run_script; swaps in the test binary.

6.4 DAC Sweep

Drives one pump. Purpose. Open-loop power-vs-speed characterisation: sweeps a pump's DAC power and plots resulting SPR, revealing the speed curve and stall point.

Displays. A scatter/line chart (X: motor power 0–4095, Y: SPR 0–30 s); green data points, amber stall triangles at the 25 s cap, a dashed stall line; a per-step status label.

Controls. Pump; Sweep; Stop. Data. dac_sweep_spr_script drives the ULP test_dac_sweep_enc routine (DAC 4095→0 in steps of 100, 1 s settle + 1 s count each); SPR = 5184/ticks, 0 ticks = stall. Swaps in the test binary.

6.5 PID Tuner

Drives one pump. Purpose. A single-purpose tuning workbench for the Simple-P regulator: pick a pump + target SPR, run for a set number of hall revolutions on the pump_test2.bin sandbox, and watch SPR convergence with per-run error statistics. (The legacy positional-PID "Test" mode and the live-"Operational" mode were removed; Simple-P is the only production regulator.)

One mode. Simple-P runs on pump_test2.bin via pid_p_regulate_script (swaps the test2 binary in, restores pump_regulator.bin on Stop). The three tuning levers are pwr/1% (step_per_pct), N (encoder pulses per measurement) and the skip-ladder VALUES (the 10 per-level idle multipliers). N + the ladder values are written only when the deployed ULP Test2 ≥ 1.3.2 exposes p_reg_pulse_count + p_reg_skip_table; older test2 builds degrade gracefully to the baked N=16 + 2idx ladder.

Displays. A polar convergence chart in SPR seconds (live + completed + historical revs, target circle, hall rim arc); measured-SPR and resulting-power histograms; a Run-History log (per-rev mean/err/EncOn%, plus a run summary with a Rev2+ line excluding spin-up); an Enc readout + status (incl. STALL/START-FAIL warnings).

Controls. Pump; Target SPR; Run; Stop; Clear; Start power; Run revolutions; N (pulses); Simple-P bounds (Kp pwr/1%, Max error%, Min/Max pwr, Max meas, Skip max/good); Skip ladder (10 comma-separated per-level values, validated). Data. The host script writes the test2 addresses by name from test2_variables.py; injects the run off the UI thread.

6.6 Parking

Drives the blood pump. Purpose. Calibrates the BP hall-switch parking position: runs test_determine_parking to measure the magnet-active bracket (in encoder ticks), then arms BP_PARKING to drive to the bracket centre plus an optional offset. BP-only.

Displays. A compass-style polar chart with a rotating needle (colour = live hall state), a filled yellow bracket arc on success, dynamic phase titles, and a status readout (pulses, revolutions, power, hall glyph; on completion: bracket ticks/degrees, elapsed).

Controls. Calibrate Parking; Stop; Offset-from-centre (0–359°). Data. determine_parking_script(user_offset) frames routed in via _MODE_PARK_CAL.

6.7 Valve-Tape

Drives the valve + tape motors. Purpose. Direct open-loop PWM control of the two main-CPU brushed motors, with live limit-switch indicators. A manual hardware-exercise tool.

Displays. Valve group (Power%, Direction, GPIO label, OPEN/CLOSED limit-switch dots, status); Tape group (Power%, GPIO label, status).

Controls. Valve Power (0–100%), Direction (open/close), Start, Stop; Tape Power, Start, Stop. Data. Indicators via update(d) (valve_open/close); drive via an inline MicroPython PWM script built in _on_valve_tape_changed (not a board_script factory; LEDC @2 kHz, PWM_MAX=65534) injected through bridge.inject(). This script replaces MONITOR_SCRIPT while a motor runs (the monitor sets those pins as inputs).

6.8 Sensors

Drives the LED rails. Purpose. Live bench diagnostics for every sensor: enables the LED emitter rails on demand, streams all sensor outputs as sparklines, and lets the operator tune fluid/tape classification cutoffs against the recent buffer. The only Control tab that actively drives the LED-enable GPIOs.

Displays. A Sensor/LED-enable card (status + 3 LED checkboxes with readback dots; Blood/Air + AC/Air share one rail); 7 sparkline cards (Blood/Air, AC/Air µV→mV; Spot, Line lux; Pressure; Humidity; Temperature) each with a numeric readout and a ~60 s trace; for the 4 classify rows, tinted y-bands + dashed cutoff lines + a live band label and a buffer percentage breakdown.

Controls. 3 LED-enable checkboxes (re-inject sensors_monitor_script with new flags); per-band cutoff spinboxes (host-side only); a Commit cutoffs → Board Config button that maps the tuned fluid state-band boundaries (midpoints, mV→µV) to the four BLOOD_SENSOR_*/AC_SENSOR_* thresholds and, after a confirmation dialog showing the exact keys/values, writes them to /board_overrides.json on the board via a one-shot raw-REPL command (pauses + resumes the live stream). The firmware-independent overlay applies at the board's next reboot (config.py; SWR-224…229) — no new firmware version. Entering the tab starts the stream; leaving it drives the rails OFF and restores MONITOR_SCRIPT. Data. {sensor:{...}} via update(d); cutoff defaults from board_config.py.

6.9 Event Log

Read-only. Purpose. Pulls the Main-CPU persistent event log (events.db AppendOnlyStore) on demand into a colour-coded table.

Displays. A 4-column table (#, Time local, Type, Message with arguments substituted), row colour by type (log/state/error/recovery/initialization/fatal-error); parse-error rows in red; a progress/result status label.

Controls. Fetch all; + New only (incremental from last_seq+1); Clear (host-side). Data. event_log_script(from_seq) (filesystem read only; no ULP addresses) via _MODE_EVENT_LOG; refuses while another test runs.

6.10 Diagnostics

Read-only. Purpose. Cross-session viewer of the board's diagnostics.csv (one summary row per session / fatal error).

Displays. An 11-column table (BP/AC Revs, BP/AC Avg SPR, Stalls, Fatal Error, FW Version, Build Date, Board UID, Session Start/End); fatal-error rows in red; a status label.

Controls. Fetch; Clear (host-side). Data. diagnostics_script() (reads the CSV; touches no ULP memory) via _MODE_DIAGNOSTICS.

6.11 Board Config

New in this revision. Read-only.

Purpose. A table of every constant in fluispotter/board_config.py — the board-type hardware configuration (GPIO pin assignments, DAC registers, I2C addresses, motor physical constants, PWM, motor power/speed, parking, dosing, PID gains, fluid-sensor thresholds, synchronization).

Displays. A two-column (Setting / Value) table with a styled section-header row before each board_config.py section; values shown verbatim (0x3a, 800_000, 5184).

Data. Parses the board_config.py source text at construction (regex over section headers + NAME = const(value), preserving order and grouping); never executes the module, so it always reflects the deployed file. Controls. None. Hardware. None (reads a repo file).

6.12 Session Log

Read-only (network). Purpose. Reviews a device's historical event stream pulled from the RPi hub's HTTP API, independent of any serial connection.

Displays. A 4-column table (#=last 6 of uid, Time, Type, Message with arguments), row colour by type (incl. warning/sample/command/settings); a status label.

Controls. Fetch; Limit (10–500); Clear. Data. Blocking urllib GET on a daemon thread to http://fluispotter.internal/synchronize/devices/<uid>/events?limit=N, marshalled back via a signal. The device UID is a module constant; this tab ignores serial connect/disconnect state.

6.13 Fluispotter (Board Registry)

Database tool. Purpose. An asset-management tab backed by PostgreSQL: register physical boards (auto-generated FSP-XXXX serial + the board's hardware MAC) and define reusable board types cataloguing features, a GPIO map, and config key/values.

Displays. A DB connection bar; a Boards table (Serial, MAC, Type, Description, Status, First Seen); a Board Types table; and per-type Feature / GPIO-Map / Config detail tables.

Controls. Add/Save/Clear/Refresh boards; Add/Save/Delete types; +/−/C on the feature/GPIO/config detail tables; Connect/Disconnect DB (non-blocking). Data. Raw SQL over a psycopg_pool (opened on a daemon thread). The only hardware touch: when adding a board it reads machine.unique_id() over the bridge (the one panel given the bridge via set_bridge()). Not on the telemetry path.

6.14 Log

Read-only. Purpose. A raw scrolling view of every JSON frame received (defined inline in main.py as _LogPanel). Deliberately the last tab. Controls. Scroll/select. Hardware. None.

7.2 Orphaned / Dead Code

• control/panels/min_spr_panel.py (MinSprPanel): fully implemented “find minimum sustainable SPR” panel, but not imported or added as a tab by main.py; its backing min_spr_script exists. Not in the shipped UI.

• encoder_panel.py contains dead dac_sweep_*/_on_dac_sweep methods referencing widgets/signals that no longer exist (DAC Sweep was moved to its own panel); they are never called. The {fp_start}/{fp_hall} frames route to optional hooks the panel does not define, so live hall level is not displayed there.

7.3 Safety & Maintenance Caveats

• Single shared link, mode-gated. Live pokes and test injects are mutually exclusive via _mode; a running test blocks log/diagnostics fetches and pump pokes. Respect this when adding panels.

• Restart after a deploy. The app caches ULP addresses at launch; the connect-time guard rejects a stale map. Restart the Control app after every ULP deploy.

• Addresses by name only. Never hardcode ULP hex; resolve from variables.py/test_variables.py/test2_variables.py.

• 5184 pulses/rev is duplicated as a local constant in several panels (Parking, Resistance Map, PID Tuner); keep in sync with the ULP main.c.

• Inverted power. power = 4095 − dac_register everywhere; scripts write the register, the UI shows power.

• Static tabs (Board Config) and the Session Log tab are not on the telemetry fan-out and need no set_connected() wiring.
