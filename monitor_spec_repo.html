1. Document Overview


This document specifies the Fluispotter Monitor Application — a macOS PyQt6 desktop app used during development to passively observe a connected Fluispotter device over USB serial. It describes the application's software structure, how it handles data, how it reflects device hardware, and the function of every tab in its UI.

It is a living document. Per the same discipline as the Device Specification Repository, every change MUST bump the version in the cover page and the Document Control table below, and add a row to the Change Log.

2. Purpose & Scope


The Monitor app is a strictly read-only telemetry viewer. It opens the device's USB-CDC serial port, reads the JSON telemetry the firmware already prints (~10 Hz), and renders it across a set of dashboards: live state machines, pump regulators, sparkline trends, valve/tape actuators, the sensor suite, the sample schedule, and an event log.

It never injects code, sends commands, or drives hardware. That active role belongs to the sibling Control App (see the Control Application specification). The two apps share a panels theme and the board_script.py library file on disk, but the Monitor app does not import or use board_script.py.

Scope: the macOS Monitor desktop app only. Firmware, ULP coprocessor, and the RPi hub are covered by the Device Specification Repository.

3.3 Threading Model

Two threads communicate by polling, not by Qt signals:

ThreadResponsibilities
Serial daemonThe SerialBridge IS a threading.Thread (started in its constructor). It performs all blocking serial I/O, parses JSON, and pushes dicts onto a queue.Queue(maxsize=2000). It never touches Qt objects. A lock guards port open/close/reconnect against the GUI thread's listen()/disconnect().
GUI threadA 100 ms QTimer fires _drain_queue (a @pyqtSlot) which drains up to 20 frames/tick via get_nowait() and updates panels — so all widget mutation stays on the main thread. A 2000 ms timer reflects bridge.error to the toolbar.

A custom sys.excepthook prints tracebacks instead of letting PyQt6 qFatal()/abort the process when a slot raises — the app survives a bad frame.

4. Data Handling


4.1 Serial Transport — SerialBridge (Passive Reader)

SerialBridge is a daemon thread that opens serial.Serial(port, 115200, timeout=0.2). Its run() loop calls readline(), strips the line, and parses only lines that both start with { and end with } via json.loads. Valid dicts are put_nowait onto the queue (silently dropped if the queue is full). Non-JSON lines (REPL prompts, debug logs) and decode errors are silently ignored.

On a SerialException (USB drop / light-sleep re-enumeration) it sets connected=False and auto-reconnects with a 0.5 s backoff: it retries the last port, then find_port() which globs /dev/cu.usbmodem* (preferred over tty.*, which can block on carrier), then tty.usbmodem*, then cu.usb*/tty.usb*. This handles the ESP32-S3 reappearing under a new device name (e.g. cu.usbmodem101 → cu.usbmodem1101).

Public surface: bridge.queue, bridge.connected, bridge.error, listen(), disconnect(), stop(). There is deliberately no write/inject method.

4.2 Telemetry Frame Format

The firmware's on-board telemetry task prints one flat JSON object per ~100 ms. A real telemetry frame is identified by the presence of the t key (a millisecond timestamp). Representative keys:

GroupKeys
Timing / statet, main_state, inv (ULP invocation counter), bp_revs, stop_ev (motor-stop bitmask)
AC pumpac_run, ac_st, ac_dac, ac_pwr (= 4095−dac), ac_hall, ac_pulses, ac_us, ac_max, ac_min, ac_kp/ki/kd, ac_target_ms
Blood pumpbp_run, bp_st, bp_dac, bp_pwr, bp_hall, bp_pulses, bp_us, bp_max, bp_min, bp_parking, bp_dosing, bp_parked, bp_kp/ki/kd, bp_bracket, bp_offset, bp_target_ms
Actuatorsvalve_en, valve_dir, valve_open, valve_close, tape_en, tape_emit, reed
Sensorsac_air, blood_air, pressure (µV), spot_lux, line_lux (lux, ~1 Hz), temp_c, rh_pct
Schedulett_n, tt_idx, tt_started, tt_chunk, dosed_at, utc, hall_ev

Power convention: ac_pwr/bp_pwr are pre-computed on the board as 4095 − dac_register (the inverted DAC power convention). The app consumes them directly.

4.3 Inbound Data Flow (Board → Panels)

firmware telemetry print  (USB-CDC, ~100 ms)
   -> SerialBridge.run()   readline + JSON validate + json.loads
   -> bridge.queue         (queue.Queue, max 2000)
   -> _drain_queue         (QTimer 100 ms, up to 20 frames/tick)
   -> _handle_frame(data)

_handle_frame always appends the raw dict to the Log tab (colour-coded: err=red, done=green, res_rev/enc_rev=amber). On an err key it returns early. Only frames containing t fan out to the live panels via update(data):

PanelUpdate policy
Live (_LiveTab)Every frame. Derives virtual BP states (PARKED/STOPPED) and a valve state (CLOSED/OPEN/MOVING/UNKNOWN) from limit switches, then calls StatePanel.update(...) and VarPanel.update(d).
ChartsOnly when the Charts tab is the current widget (performance optimisation — histories do not accumulate in the background).
Tape & Valve, Sensors, Sampling, State LogEvery frame.
Config, Board Config, LogNot fed via update() (Config/Board Config are static; Log is fed inside _handle_frame).

4.4 Outbound Path (None — Passive Listener)

The Monitor app has no outbound command path. The SerialBridge exposes no write method and main.py never sends anything to the board. This is a deliberate safety property: running the Monitor app cannot alter device state.

4.5 Enabling the On-Board Telemetry Task

The firmware telemetry task that produces the JSON is enabled out-of-band, not by the app: place a /telemetry flag file on the device (e.g. rshell touch /pyboard/telemetry) and reset. The Monitor app cannot enable it.

5. Hardware Interaction


The Monitor app interacts with hardware only by observation — everything it shows is decoded from firmware telemetry; it drives nothing. The hardware reflected in the UI:

SubsystemWhat the app reflects (read-only)
AC & Blood pumpsRun flag, ULP state, DAC drive register and derived power, hall switch (0 = magnet active), encoder pulses/batch and elapsed µs → actual seconds-per-rev (using 5184 ticks/rev), regulator gains and target.
ValveEnable, direction, and the open/close limit switches (GPIO 42 / 46, active-low) → CLOSED / OPEN / MOVING / UNKNOWN.
Tape reelMotor enable (GPIO 41) and tape emitters (GPIO 43).
Reed / on-switchGPIO 5 (pull-up, active-low): 0 = active/closed.
Fluid / pressure ADCsBlood-air (GPIO 7), AC-air (GPIO 6), Pressure (GPIO 3), reported in µV.
Optical spot/lineVEML6035 at I2C 0x3A (spot) and 0x29 (line); reported in lux.
Temp / humiditySHT4X at I2C 0x44.
ULP coprocessorInvocation rate (from the inv counter) and motor-stop events.

6. Tab Reference


Tabs are listed in display order (the order of addTab() in main.py). All are read-only.

6.1 Live

Composite tab (_LiveTab) = StatePanel (left) + VarPanel (right).

Purpose. At-a-glance view of every device state machine plus a side-by-side AC-vs-Blood pump regulator table and a column of 60-second sparklines.

Displays. StatePanel: the 12-state main-CPU machine (INITIAL…FINISH), session sub-state (IDLE/TRIGGER/DOSING) and the 8-step dose sequence (only highlighted in SESSION/DOSING), the ULP AC pump (IDLE/RUNNING) and Blood pump (IDLE/RUNNING/DOSING/DOSE COAST/PARKING/PARKED/STOPPED) states, the BP flush cycle (ACTIVE 2 min / IDLE 8 min / SUSPENDED), valve (CLOSED/OPEN/MOVING) and tape reel (STOPPED/RUNNING). The active state in each list is highlighted. VarPanel: an AC/BP table (Running, State, Power bar + value, DAC register, Hall, Pulses/batch, Elapsed µs, Actual SPR, Avg SPR error, decoded Stop events, PID gains, ULP invocations, BP bracket/offset) plus sparklines (AC/BP power with hall-tick overlay, AC/BP SPR, Valve, Tape, WiFi sync, ULP rate).

Data. update(d) from _LiveTab; several BP/valve states are derived host-side, not emitted by firmware. Controls. None. Hardware. Observe-only.

6.2 Charts

Purpose. A full-width column of 13 scrolling 60-second sparklines for an at-a-glance time-series of device state.

Displays. AC power, BP power (each with an amber hall-tick overlay), AC SPR, BP SPR, Valve, Tape reel, WiFi sync, ULP invocation rate, AC-air µV, Blood-air µV, Pressure µV, VEML spot lux, VEML line lux. Each is a 600-sample (~60 s) rolling trace.

Data. update(d) — but only while the Charts tab is visible (perf). SPR = us×5184/pulses/1e6; ULP rate from Δinv/Δt; air/pressure/lux are guarded so missing/None values skip rather than plotting 0. Controls. None. Hardware. Observe-only.

6.3 Tape & Valve

Tab title literal is the truncated Tape & V....

Purpose. Diagnostic view of the valve motor, tape-reel motor, and reed switch.

Displays. A valve banner (OPEN/CLOSED/MOVING/UNKNOWN from the two limit switches + enable), valve detail rows (enable, direction, open switch GPIO 42, close switch GPIO 46), a tape-reel state (RUNNING/STOPPED from tape_en) with enable (GPIO 41) and emitters (GPIO 43), and an on-switch/reed card (GPIO 5, active-low).

Data. update(d) keys valve_*, tape_*, reed; missing keys render as ‘—’. Controls. None. Hardware. Observe-only (switch polarity is active-low: 0 = active).

6.4 Sensors

Purpose. A passive dashboard of every host-readable sensor, each card showing latest + previous reading, a trend arrow, and a ~30 s mini-sparkline.

Displays. Blood-air (µV), AC-air (µV), Spot (lux), Line (lux), Pressure (µV), On-switch/Reed (digital), and Humidity/Temperature (SHT4X, °C and % rH). Trend arrow appears only once a non-zero previous value exists.

Data. update(d), each key guarded by in d; humidity updates only when both temp_c and rh_pct are present. Controls. None. Hardware. Observe-only.

This is the read-only Monitor variant. The Control app's Sensors tab additionally drives the LED rails and offers cutoff tuning — see the Control specification.

6.5 Sampling

Purpose. Observability for the blood-pump sampling subsystem: reconstructs the sample time-table, tracks live BP hall state and revolutions, and logs every hall transition.

Displays. A Sample Schedule table (#, Offset, Samples, Planned UTC, Actual UTC, status) assembled from round-robin tt_chunk frames; a BP hall summary card (hall state, revolutions, SPR target, last elapsed µs, pulses/batch); and a Hall Switch Events table (Time, Segment s, Pulses, Revolution), newest-first, capped at 500 rows with the top 7 tinted to mirror the firmware's 7-deep sample-history deque.

Data. update(d) (schedule, summary, hall_ev). Actual completion times are inferred client-side when tt_idx advances (stamped with dosed_at). Controls. None. Hardware. Observe-only.

6.6 State Log

Purpose. An append-only, colour-coded log of every state-machine transition and motor/actuator event, emitted on edge (value change).

Displays. Timestamped (UTC) lines for: main-CPU STATE transitions (blue), AC/BP pump transitions (amber), BP FLUSH cycle (cyan), SESSION sub-state and DOSE STEP (deep orange), AC/BP MOTOR start/stop (green), VALVE and TAPE events (purple), BP DOSE/PARK arm/complete (amber), and SCHEDULE / SESSION START / SAMPLE collected lines (deep orange). Capped at 5000 lines.

Data. update(d) with per-field _prev_* edge detection; state-name maps imported from state_panel.py. Controls. Clear button (clears the text area only). Hardware. Observe-only.

6.7 Config

Purpose. A static reference card of firmware/board compile-time constants (pump speeds, timeouts, PID gains, sensor thresholds, dosing/parking geometry, motor/hardware constants).

Displays. Sectioned cards: Blood Pump, AC Pump, PID Gains, Dosing & Parking, Sensor Thresholds, Motor & Hardware, Timeouts & Intervals.

Data. Hard-coded literals — no telemetry, no file read. Controls. None. Hardware. None.

Caveat: because values are transcribed by hand, they can drift from firmware. The newer Board Config tab (§6.8) avoids this by parsing the source file live.

6.8 Board Config

New in this revision.

Purpose. A read-only listing of every constant in fluispotter/board_config.py — the board-type hardware configuration (GPIO pin assignments, DAC registers, I2C addresses, motor physical constants, PWM, motor power/speed, parking, dosing, PID gains, fluid-sensor thresholds, synchronization).

Displays. Section cards (one per board_config.py section header) laid out in two balanced columns, each card listing its NAME = value rows. A header shows the board identity and the live count (e.g. “68 constants in 11 sections”).

Data. Parses the board_config.py source text at construction (a regex captures section headers and NAME = const(value) lines, preserving grouping and order; the literal value, e.g. 0x3a/800_000, is shown verbatim). It never executes the module, so the deployed config is always reflected without drift. Controls. None. Hardware. None (reads a repo file).

6.9 Log

Purpose. A raw scrolling view of every JSON frame received, for debugging.

Displays. Each frame as a line, colour-coded (err=red, done=green, res_rev/enc_rev=amber). Data. Fed directly inside _handle_frame for all frames (defined inline in main.py as _LogPanel). Controls. Scroll/select. Hardware. None.

7.3 Maintenance Caveats

• The 5184 pulses-per-rev constant is hard-coded in several panels (Charts, VarPanel) rather than imported; keep it in sync with the ULP.

• The Config tab's values are hand-transcribed; prefer the live Board Config tab as the source of truth.

• The module docstring's tab list omits the Charts tab and is slightly stale relative to the actual addTab() calls; the tab order in §6 is authoritative.

• Tab order equals the order of addTab() calls; static tabs (Config, Board Config) must NOT be added to _handle_frame's update fan-out (they have no update() method).
