Design Note — ULP Cooperative Scheduler (non-blocking single main loop)

Status: Proposal / design (branch ulp-scheduler-redesign) Date: 2026-07-24 Author: Sten (concept) + Claude (analysis) Scope: esp32/pump_regulator/main/ulp/main.c operational binary; companion firmware in fluispotter/pump_regulator.py / fluispotter/fluispotter.py. Motivates fixes for: #48 (pad-clock blindness), #55 (silent AC restall), #56 (BP park reports done while turning).

1. Problem

The operational ULP is already a 1 ms cooperative dispatcher — set_wakeup_period(1000) (pump_regulator.py:349); main() runs ac_tick(); bp_tick(); then halts and sleeps. For steady-state regulation nothing holds the controller. But dose, coast, and park break that model: one bp_tick() invocation spins internally for the whole operation. The op 1.12.0 comment states it verbatim:

"BP_DOSING / BP_DOSE_COAST / BP_PARKING block the ULP for the whole dose (~10 s), coast (5 s) and park (≤30 s), so ac_tick() never ran there." (SWR-271)

ac_busy_regulate() is a hack bolted on to service the AC inside the BP's spin. Those multi-second blocking windows are where every current bug lives:

  • #56 — the park spins for seconds; the pad-clock gate persists through the final HALT → DAC7574 holds its last DRIVE value → motor keeps turning while a level-based hall read latches "home found" → clean park reported, no timeout.
  • #55 — ac_busy_regulate deliberately skips stall detection; the silent-anticoagulant window exists only because BP hogs the loop during dose/park.
  • #48 dev.0.4 — the deep dose→coast→park→ac_busy call chains blew the ULP stack canary.

The disease is the blocking window, not any single bug.

2. Proposal

A single flat, non-blocking cooperative main loop on the ULP. Every function is a state serviced by one small step per iteration; nothing spins internally for more than a few µs. All long operations (dose advance, coast, park, kick, stall recovery) become persistent sub-state advanced one step per loop. Priority is service ordering, not preemption: both motors are must-service-every-loop (no starvation — this deletes ac_busy_regulate); telemetry and adaptive tuning are the deferrable slack near a deadline.

2.1 Encoder counting — spike result (2026-07-24): the counter is CPU-side, not ULP-side

Git archaeology of Mirza's counter work (spike, "the hardware counter Mirza tested last year") settles this and it is not what the premise assumed:

  • Mirza implemented hardware pulse counting May 24 – June 6, 2025 (2a85510 "Experimental micropython build with esp32 pcnt" → 9d318c9 "Build micropython v1.25.0 with esp32 pulse counter" → 20edbe0 "Initial pcnt implementation" → 0c265ab "Refactor pulse counter initialization"). It is CPU-side esp32.PCNT — the PumpEncoder wrapper (pulse_counter.init/.value/.start/.stop) in fluispotter.py, needing a custom MicroPython v1.25.0 build with the esp32 PCNT module. It comes from the era when the pumps were regulated in MicroPython on the main CPU.
  • No ULP commit has ever used a hardware counter — verified across all branches and all history. The ULP RISC-V regulator (from 1aa9d2c, 2026-04-02, the first Claude-era ULP code) has always bit-banged the encoder via ulp_riscv_gpio_get_level (5184 steps/rev quadrature, polled in busy windows). esp32.PCNT still exists in fluispotter.py but is the CPU-side leftover from before the ULP offload.

So "hardware counters are available to the ULP" was a conflation: the counter was real but lived on the CPU; when regulation moved to the ULP it was left behind and the ULP bit-bangs.

2.1a PROBE RESULT (2026-07-24, bench, DECISIVE): the ULP CANNOT read PCNT

Built a TESTOP peripheral-read probe (a TEST_PEEK that loads *(uint32_t*)peek_addr from the ULP and publishes the value; probe-only mode so no deep stack / no canary confound) and ran it live on the idle board. Address matrix, ULP-read vs CPU-read of the same register:

Register Domain CPU read ULP read Match
RTC_CNTL_STORE0 0x60008050 RTC (control) 0xCAFE1234 0xCAFE1234 ✅
RTC_CNTL_STORE1 0x60008054 RTC (control) 0x1234ABCD 0x1234ABCD ✅
PCNT_DATE 0x600170FC HP/APB 0x18072600 0x600170FC ❌
PCNT_U0_CNT 0x60017030 HP/APB 0x00000000 0x60017030 ❌
SYSTEM_DATE 0x600C0FFC HP/APB 0x02101220 0xF0EF4545 ❌
UART0_DATE 0x60000078 HP/APB 0x03700000 0x8F7516FD ❌

The ULP reads RTC-domain registers perfectly (both controls exact) but every HP/APB peripheral read fails — and for PCNT the ULP returned the address itself (0x600170FC for addr 0x600170FC), the textbook signature of a load that never reaches the bus. Conclusion: the ESP32-S3 ULP RISC-V cannot access the HP peripheral register space; PCNT is unreachable from the ULP. (Probe: scratchpad/ulp_peek_probe3.py; reusable "can the ULP read address X" tool.)

Therefore the fully non-blocking, one-tiny-step-per-loop endpoint (Sten's counter-compare loop) is NOT feasible with PCNT. The redesign is bounded to the HYBRID (§7 step 2 / §2.1 below): keep bit-banging the encoder, but in short bounded poll windows (one edge-batch, tens of ms) with a fair dispatcher, instead of blocking for seconds. All the correctness wins survive; only the "read a counter each loop instead of polling" optimisation is off the table.

Residual (low-probability) avenue: an RTC-domain counting mechanism the ULP can reach (the ULP reads RTC fine) — but no RTC-domain pulse counter is wired to the encoders, so this needs new hardware/routing, out of scope for a firmware redesign.

Consequences for this design (endpoint now decided = HYBRID, per §2.1a): - The correctness wins (non-blocking, no AC starvation, closed-loop park — #48/#55/#56) need no hardware counter: bounded bit-bang poll windows (the hybrid, §7 step 2) deliver them. Counting stays exact by keeping the poll window short enough to catch every edge (Sten's "faster than ½ edge time"), just no longer for seconds. - The fully non-blocking, one-tiny-step-per-loop endpoint (Sten's counter-compare loop, §2.2) is ruled out: §2.1a proved the ULP cannot read PCNT. §2.2 below therefore describes the hybrid shape — the MoveTo counter is the ULP's own bit-bang edge tally maintained inside a bounded per-window poll, not a hardware-counter register read.

2.2 Loop skeleton (Sten's structure, refined)

loop (while any pump ACTIVE):
    now = rtc_ticks()

    # --- hall flags: EDGE/motion-gated, not bare level (see §4, #56) ---
    if bp_hall rising AND bp_encoder advanced:  set BP_HALL flag
    if ac_hall rising AND ac_encoder advanced:  set AC_HALL flag
    service BP_HALL / AC_HALL flags   # revolution count, home detect

    # --- BP: highest priority is a MoveTo (dose advance / park) ---
    if BP.move_to_active:
        # a MoveTo is SimpleP-toward-a-target, NOT a bare counter watch:
        regulate BP speed toward target SPR (SimpleP, measured dt)
        if BP.counter >= BP.move_target:   call BP.move_handler()   # HALT + next sub-state
    else:
        service BP SimpleP (hold speed / idle)

    # --- AC: always serviced, every loop (never starved) ---
    if AC.move_to_active: ... same shape ...
    else: service AC SimpleP

    # DAC writes only when the command value CHANGES (see §5, #53 contention)

Key refinements to the raw sketch:

  1. MoveTo is not an either/or with SimpleP. A dose advance must regulate speed (SimpleP) while watching the counter — otherwise the move runs open-loop. MoveTo = "SimpleP toward a target, stop at the target," not "watch a counter instead of regulating."
  2. Hall flags must be edge/motion-gated, not bare level. The current level test (bp_hall == ACTIVE_LEVEL) is exactly what lets a frozen-high read false-latch "home" in #56. Flag on the rising transition AND require encoder motion since the last home, so a stuck level cannot report a park.
  3. Closed-loop stop. bp_parked / bp_hall_detected must be gated on bp_park_enc_total > 0 (real encoder motion) — a zero-motion "park" can never report success. This is the structural cure for #56 and should ship even ahead of the full scheduler.

3. Adversarial check — "no reason for the ULP to sleep at all"

The proposal came with: "we should not use 1 ms ticks; no good reason for the ULP to be sleeping at all." Checked adversely, this is directionally right but wrong as an absolute.

The correctness win is from NON-BLOCKING, which is orthogonal to sleeping. Everything §2 buys — bounded gate exposure, no AC starvation, closed-loop park, shallow stack — comes from "each iteration does one small step and returns." You get all of it whether the loop spins continuously OR wakes fast, does one step, and sleeps. "Never sleep" and "never block" are different properties; only the second one fixes the bugs.

Where never-sleeping genuinely helps (narrow, real): stop-precision latency. If the loop duty-cycles at period T, worst-case MoveTo overshoot includes up to T of sleep before the loop notices counter >= target. Spinning continuously removes that sleep-period jitter — the only latency left is one loop iteration. So spin continuously while actively moving/regulating ** for tight dose/park stop precision. Valid — but scoped to active motion.

Where never-sleeping hurts: battery endurance. This is a battery device with a spec'd endurance (44 h at ~24.9 mA average, 2026-07-18). Most of a session's wall-clock time is idle — flush REST (8 min pump-off), between-sample gaps, AWAIT_SESSION. During those windows a continuously-spinning ULP burns core current (est. ~0.5–1 mA continuous vs ~0.1 mA at the current ~10 % duty) for zero benefit — there is nothing to regulate. Against a small idle budget that is a meaningful percentage hit, and it is pure waste.

Verdict: Don't sleep while working; sleep while idle. Kill the 1 ms blocking-tick model (the user is right that it is bad), but make ULP activity state-driven:

  • Any pump ACTIVE (regulating / dosing / parking / moving / kicking): run the fast non-blocking loop continuously — no set_wakeup_period gaps, minimum stop latency.
  • Both pumps IDLE: drop to a low-power path (sleep, or a slow heartbeat tick) co-scheduled with the CPU's own lightsleep, woken by a CPU command flag or a hall event.

This keeps the endurance win and deletes the blocking windows. "1 ms tick" dies; "sleep" survives, but only for genuine idle.

4. Loop-rate requirement (with hardware counters)

  • Counting: exact regardless of loop rate (hardware counter). No "faster than edge time" needed just to not lose edges.
  • Stop precision (the MoveTo overshoot): worst-case overshoot ≈ (edge rate at the stop speed) × (loop period + HALT latency). Dose metering happens at slow controlled speed (SPR 16–20), so the edge rate at the stop point is low and even a modest loop rate overshoots by <1 edge. The requirement bites only if you must stop precisely during fast motion. Sten's "faster than ½ edge time" is the right rule and, at dose speed, is easily met.
  • Control response: SimpleP must use measured dt (rtc_ticks delta per iteration), not an assumed fixed timestep, because a continuous loop has variable iteration time. The code already publishes ulp_now_ticks every pass — extend that to the control law.

5. Interactions and cautions

  • #53 (INT_WDT storm) — do NOT resurrect the ULP-side clock defense. #53 was the 1 kHz SENS RMW (DEFEND_CLOCK) from the ULP colliding with CPU interrupts-masked SENS writers. A faster loop must NOT re-assert SENS_IOMUX_CLK_EN from the ULP. Keep clock defense CPU-side (SWR-299) and extend it to cover the park poll loops (the #56 gap). The scheduler shrinks #48's blast radius (a gate hits one step, not a 30 s window) but does not by itself stop the CPU clearing the gate.
  • RTC-domain bus contention scales with loop rate. The DAC7574 writes go over RTC I²C (GPIO1/2, RTC pads). A faster loop writing the DAC every iteration increases RTC-domain traffic competing with CPU rtc_gpio claims — the same contention family as #53. Mitigate: write the DAC only when the commanded value changes, not every iteration.
  • Stack headroom (helps op 1.16.0). A flat dispatcher with persistent sub-state is shallower than today's deep dose→coast→park→ac_busy chains — directly easing the 768 B canary gate that has blocked op 1.16.0. The .stack_canary sentinel + firmware per-tick check stay armed through the migration.
  • Dose-volume accuracy is non-negotiable. Dose = an exact encoder-edge count = patient safety (anticoagulant-diluted blood). The MoveTo handler must stop on the hardware count with bounded overshoot and record actual-vs-target; regression A/B must prove exact volume parity vs the current binary.

  1. Now, low-risk (fw 0.1.143, own track): land the closed-loop #55/#56 fixes without the rewrite — gate bp_parked on bp_park_enc_total > 0, extend defend_pad_clock() into the park poll loops, add the AC stall-count audit. Stops the bleeding.
  2. Prototype on the TestOp track (pump_testop.bin, MAJOR 9): build the non-blocking dispatcher; operational binary stays frozen until proven. Start with the dose/coast/park steps (the blocking windows), keep SimpleP math intact.
  3. Then bump operational and roll in.

8. Open questions

  • [ANSWERED 2026-07-24, §2.1 + §2.1a] Mirza's counter was CPU-side esp32.PCNT, never ULP-side. The bench peek probe then PROVED the ULP RISC-V cannot read PCNT (or any HP/APB peripheral) — RTC-domain reads exact, all HP reads fail. Endpoint = HYBRID, decided.
  • Idle-sleep trigger: exact "both pumps idle" predicate and wake source (CPU command flag vs hall EXT1) that co-schedules ULP sleep with CPU lightsleep without reintroducing a wake gap during an active MoveTo.

9. Increment 1 — non-blocking PARK (first TestOp build spec)

Why park first: it is the simplest of the three blocking operations, it directly fixes #56 (BP reports parked while turning), and it frees AC from the park-window starvation half of #55 — all in one contained, benchable slice. Operational binary stays frozen; this lands on TestOp (MAJOR 9) and only rolls in after bench A/B.

9.1 What blocks today (op 1.15.0, bp_tick() case BP_PARKING)

Two internal loops run the whole park in ONE bp_tick() invocation: 1. Drive loop — while (bp_parking && !hall_found && bp_park_enc_total < PARK_ENC_TICK_LIMIT && rtc_ticks() < bp_park_deadline) calling bp_drive_window(op_p_pulse_count, …, watch_hall) repeatedly (≤30 s). ac_busy_regulate() is called inside it to keep AC alive — the hack. 2. Offset coast — while (remaining > 0 && rtc_ticks() < t_offset_end) counting bp_park_offset_ticks + bp_park_user_offset edges past the hall, under power (≤5 s).

bp_drive_window() itself is the bounded atomic unit (collects ≤op_p_pulse_count edges or times out at calc_meas_timeout_us, ~tens of ms) — it must busy-poll to catch fast edges (bit-bang; §2.1a proved no HW counter). It is the loops around it that block.

9.2 Decomposition — one bounded window per tick

Split BP_PARKING into two sub-states; do at most one bp_drive_window() (or one offset window) per bp_tick(), then return so ac_tick() runs on the next invocation. All loop-carried state is already _PRIV static (bp_park_enc_total, bp_park_deadline, bp_park_last_level, bp_has_started, bp_recovery_signaled) — persists across ticks for free; add bp_park_offset_remaining, bp_park_offset_deadline, bp_park_already_home.

BP_PARKING (drive):                         # one window/tick
  if !bp_parking: halt+enc_off; BP_IDLE; break
  hall_found = (bp_hall_edge_service(0) == ACTIVE_LEVEL)     # continuing check
  if hall_found:            -> enter_offset_or_complete(already_home)
  elif enc_total>=LIMIT or rtc>=deadline: -> complete(timeout)
  else:
    if bp_dose_park_kick():                 # still spinning up? retry next tick
      edges = bp_drive_window(op_p_pulse_count, &bp_park_last_level, true, &hall_found)
      bp_park_enc_total += edges
      if edges==0 and !hall_found: signal MOTOR_STOP_BP; bp_has_started=false
      if hall_found: -> enter_offset_or_complete(already_home=false)
    break                                   # AC serviced next tick

BP_PARK_OFFSET:                             # one window/tick (new sub-state)
  if !bp_parking: -> complete(cancelled)
  drive one bounded offset window: count edges into bp_park_offset_remaining--
  if bp_park_offset_remaining==0 or rtc>=bp_park_offset_deadline: -> complete(success)
  break

complete(reason):                           # halt + closed-loop verify + publish
  DAC_HALT; BP_ENABLE=0; BP_ENC_ENABLE=0; bp_dac_value=DAC_HALT
  # ── #56 CLOSED-LOOP STOP: prove the motor actually stopped ──
  quiescent = post_halt_encoder_quiet(POST_HALT_CHECK_US ~50ms)   # no edges after halt
  bp_hall_detected = hall_found ? 1 : 0
  bp_parked = (hall_found && bp_parking_calibrated
               && (already_home || bp_park_enc_total > 0)          # not blind
               && quiescent) ? 1 : 0                               # actually stopped
  if hall_found && !quiescent: motor_stop_events |= MOTOR_STOP_BP  # halt didn't take → fault, not silent
  bp_parking=0; bp_pump_running=0; BP_IDLE; wakeup_main_cpu()

9.3 What this fixes / changes

  • #56 (reports parked while turning): two new gates at complete — bp_park_enc_total>0 (park wasn't blind) AND a POST_HALT encoder-quiescence re-read (the halt actually took; catches the pad-gate-swallowed-HALT / stuck-DAC case). A non-stopping "park" now reports bp_parked=0 and raises MOTOR_STOP_BP instead of a silent success.
  • #55 (park-window half): ac_busy_regulate/ac_busy_hall_service are removed from the park path — AC is serviced by the normal ac_tick() between windows now, with its full stall detection live (no silent window). ac_busy_hall_service stays inside bp_drive_window only (the ~tens-of-ms window still needs AC-hall capture).
  • #48 blast radius: the ULP returns to main() every ~window, so the firmware-side defend_pad_clock() (SWR-299) park-poll re-assert can actually cover the park — impossible while the ULP blocked 30 s in one shot.
  • Headroom: deleting the deep park → ac_busy_regulate → run_simple_p chain from the park path reduces max stack depth on that path — expected to recover headroom (helps op 1.16.0).

9.4 Acceptance (bench A/B, TestOp vs frozen operational)

Autonomously provable: compiles; build_verify_ulp headroom ≥ operational; state machine transitions + non-block verified via the peek/telemetry (no motor). Bench-gated (needs the owner driving pumps): (1) parks AT the dead-point every time (SWR-132); (2) closed-loop stop — a deliberately gate-blinded park reports bp_parked=0+fault, never silent success; (3) AC never starved during park (its stall events now appear if they occur); (4) park time + overshoot within tolerance vs operational; (5) ≥20 park cycles, zero regression. Only then roll into operational + bump op version. Increments 2 (dose) and 3 (flush drive / coast) follow the identical pattern.

9.5 STATUS — dev.0.7 built + on-board proven (2026-07-24)

Autonomous gates PASS. Built on the TestOp track (dev.0.7, wire MAJOR 9). The frozen operational binary is byte-identical (BP_PARK_OFFSET enumerator is TESTOP-guarded; proven by op-preprocess diff = 0 and op-binary sha 23c471f1… compared vs a570479). On-board command channel proof (scratchpad/dev07_verify.py): writing BP_PARKING=1 drives the new state machine IDLE → BP_PARKING → IDLE, one bounded bp_drive_window() per tick (ULP keeps ticking — I read state and cancel mid-park), encoder accumulates, hall is detected, and the #56 closed-loop gate correctly withholds bp_parked without calibration. Canary clean throughout.

Two findings worth carrying forward:

  • The "canary trips (ovf=1)" scare was a verify-harness bug, not headroom. Loading /pump_testop.bin while the board still ran the operational variables.py made _load_and_start's stack pattern-fill clamp to the operational canary (184 B too low), clobbering the testop binary's gpio_initialized + canary → spurious latched ovf=1. The real testop deploy (deploy_testop_serial) writes the matching testop_variables.py, so the boot path is correct; only the ad-hoc runtime-swap harness had to patch ULP_STACK_CANARY.
  • Headroom is tight: the deep park chain needs 384 B and overflows at 368. dev.0.7 keeps DEFEND_CLOCK retired partly to free those 16 B (SWR-299 already moved the pad-clock defense CPU-side). This is the concrete argument for Increments 2–3: decomposing the dose/coast blocking loops removes the deep chains and grows real stack margin, so the ~4 B margin here stops being a constraint. Until then the deep DOSE path is unverified on the TestOp binary at 384 B.

Control-app compat: FLUISPOTTER_ULP_MAP=testop points the whole Control app at testop_variables.py (default operational, production path unchanged); the connect-time check expects MAJOR 9 and fails safe on a map/board mismatch. Owner drives pump + park from there.

Bench gates (1)–(5) remain owner-driven (need the motor). Deploy for the bench test: python3 output/deploy_testop_serial.py then power-cycle when it says WAITING; launch the Control app with FLUISPOTTER_ULP_MAP=testop.

10. Increments 2–3 (dose/coast) + Calibrate — dev.0.8, on-board proven (2026-07-25)

Increments 2–3 — non-blocking dose + coast. BP_DOSING and BP_DOSE_COAST were the last ULP-owning while-loops (~10 s dose, 1 s coast). Decomposed to one bounded window per tick; the AC is serviced by ac_tick() between windows, so the in-loop ac_busy_regulate slice is dropped from the testop dose. That removed ac_busy_regulate's only testop caller, so --gc-sections reclaimed the whole function — testop stack headroom 384 → 768 B (the decompose-first move that bought the room for calibration, exactly as §9.5 predicted). Zero new .bss (dose/coast reuse existing vars). On-board: dose ran DOSING→COAST→IDLE with INITIALIZED advancing every poll (0 frozen = never blocks), coast = DOSE_COAST_US exactly, canary clean.

Calibrate Parking — BP_PARK_CAL (enum 6), the cooperative decomposition of test_determine_parking. Command bp_park_calibrating (CPU sets, ULP clears). Spins up through the adaptive bp_dose_park_kick — the fixed PARK_CAL_DAC alone cannot break the rotor free of a hard spot, only the escalating kick can (that was the first live failure: motor never turned) — then holds PARK_CAL_DAC and measures the hall-active bracket over the 4-phase sweep (A reach / B exit / C full-rev / D bracket; hall active-LOW). Publishes bp_hall_bracket_ticks + bp_park_offset_ticks = bracket/2 only when the full rev lands in the locked [4992,5376] gate (SWR-119/120); the CPU sets bp_parking_calibrated (SWR-129). The blocking test_determine_parking is now #ifndef ULP_TESTOP_BUILD (reclaims its ~0.7 KB .text; SWR-503 already scopes it operational-only).

Gap-undercount finding: counting encoder edges across cooperative-window gaps undercounts by ≈ gap × PULSES_PER_REV / window (~250 edges at a 40 ms window — right on the gate floor). Cal runs pre-session (AC idle), so it uses a larger CAL_WIN_US (200 ms) window → undercount ~50, enc_total comfortably inside the gate. The bracket/offset stay self-consistent with the park's own edge counting (the offset error from the window-size mismatch is < 1°).

On-board: dose non-blocking PASS; calibration 3/3 PASS (brackets 366–384, spread 18, offset = bracket/2 each, enc_total 5098–5111 all in gate, non-blocking, canary clean, headroom 512 B). Full Control-app path end-to-end (the Parking panel's determine_parking_script in testop mode): calibrate → bracket=369 offset=184 → bp_parking_calibrated=1 → park at bracket centre → parked=1. Operational binary byte-identical throughout; make verify 143/0.

Owner bench test: python3 output/deploy_testop_serial.py (power-cycle when it says WAITING) → Control app with FLUISPOTTER_ULP_MAP=testop → Parking tab → Calibrate Parking. Remaining owner-gated: confirm the calibrated park lands visually centred in the hall zone, and ≥N calibrate/park cycles with a stable bracket.

11. THE FOLD — dev.0.10, one continuous main loop, all states per-pass (2026-07-25, on-board proven)

Sten's directive: "Why not drop the windows we are replacing? Just build from the ground up. only the nonblocking functions." The dev.0.7–0.9 ladder kept each state's internal window and only wrapped a continuous loop around them (F1) — which was headroom-negative (the loop's code cost pushed the testop canary to 368 B, below the ~450 B the cal's spin-up chain needs; the cal canary-tripped). The fold does the opposite: it deletes the blocking regulators and rebuilds every state on one per-pass primitive.

Model. main() runs ac_tick(); bp_tick(); back-to-back in a do { … } while (!sched_idle()) loop (dev.0.9), sleeping one wake period only when both pumps are idle. Every moving state now does one encoder (+hall) read per pass instead of a bounded window:

  • seg_pass(seg_t*, …) — the single generic drive core. Reads the encoder once; on a rising edge it accumulates a Simple-P segment of op_p_pulse_count intervals and, when the segment closes, applies the unchanged run_simple_p law + writes the DAC. Thin bp_drive_pass/ac_drive_pass wrappers bind it to each pump's vars. seg_stalled() = no edge for the SPR-scaled first-edge window.
  • BP_DOSING/BP_DOSE_COAST/BP_PARKING/BP_PARK_OFFSET/BP_PARK_CAL and AC_RUNNING/ BP_RUNNING all call the per-pass primitive. Target-crossing is edge-exact (no window overshoot); the loop polls ~20 kHz, far faster than edges arrive, so counting is gap-free.
  • The only blocking helper kept is the ≤50 ms adaptive kick (try_kick_start, via bp_dose_park_kick/ac_kick) — the load-bearing spin-up that breaks the dead-point free. Untouched.

Headroom by DELETION (the whole point). With no per-pass caller left, --gc-sections drops regulate_pump (800 B), bp_drive_window (510 B), sample_encoder (inlined into the kick), ac_busy_regulate + ac_busy_hall_service — ~1.5 KB. Testop headroom 368 → 1804 B (4× the cal's peak). No shaving the loop, no touching the kick.

The continuous-loop I2C trap (critical). A bit-banged ULP I2C DAC write costs ~1 ms. Any DAC write done every pass throttles the loop below the edge rate → gross undercount (first cal run: enc_total 1288 vs 5184, at only 485 passes/s). The DAC latches, so: the cal writes PARK_CAL_DAC once (guarded on bp_dac_value), and AC_IDLE/BP_IDLE skip the redundant per-pass HALT once stopped. After that the cal loop runs ~20 kHz and counts gap-free. seg_pass already writes only on a segment close (~1/16 edges), so steady regulation is unaffected. PARK_CAL no longer needs CAL_WIN_US — gap-free polling ends the §10 edge-undercount at its source.

On-board proof (dev.0.10, all canary-clean, headroom held): - Cal: enc_total 5180 ≈ PULSES_PER_REV 5184 (gap-free, more accurate than §10's windowed 5098–5111), bracket 380, offset 190 = bracket/2, in the [4992,5376] gate, phases [0,1,2,3]. - Dose: 1003/1000 edges (edge-exact + coast) → IDLE. - Park: drove 3783 edges → hall=1, closed-loop parked=1. - BP-RUN / AC-RUN: both RUNNING, DAC regulating (BP ~1400, AC ~2100), bp_last_pulse_count=16 (segments closing → run_simple_p firing).

Operational binary byte-identical (sha 23c471f1…, all fold code #ifdef ULP_TESTOP_BUILD); make verify 143/0.

11.1 dev.0.11 — the CLEAN fold: nothing blocks + the skip ladder is back (2026-07-25, on-board proven)

Both dev.0.10 deferrals landed, closing the fold out (Sten: "Skip ladder and fold in the kick to be non-blocking — we want this clean").

(1) The last blocking helper is gone. try_kick_start's ≤50 ms blocking sample_encoder wait is folded into a per-pass first-edge kick (try_kick_pass): the SAME escalating continuous hold (drive at *dac_start, +power+persist every ~50 ms without a first edge, motor never de-energized — SWR-132 / 1.9.0) spread across continuous-loop passes. With no caller left, --gc-sections drops try_kick_start AND sample_encoder — the ULP now blocks nowhere. (bp_dose_park_kick is #ifdef-split: op keeps try_kick_start, byte-identical.)

(2) The skip ladder is restored — battery profile back. The pure-continuous dev.0.10 loop spun the CPU whenever a pump ran (sched_idle only slept when everything was idle), a real regression vs the old sleep-between-ticks model. dev.0.11 reintroduces the adaptive skip in folded AC/BP RUNNING: after each closed Simple-P segment the encoder is held OFF for the ladder interval, expressed as a wall-clock deadline (*_skip_hold_until) not a pass count — robust because a count would blow through while the other pump keeps the loop spinning. sched_idle() now returns true (sleep one wake period) whenever every active pump is idle or inside a skip-hold, and false (spin gap-free) only while a pump is actively measuring — so the loop bursts fast to catch the N edges, then sleeps through the hold (hall still serviced per wake). Dose/park/cal never skip, so they stay edge-exact.

Headroom 1804 → 956 B (the kick fold + ladder cost ~850 B; still 2× the cal peak). On-board (canary clean throughout): park → parked=1, cal enc_total 5162 ≈ 5184 in-gate (bracket 360, offset 180), BP+AC steady regulation through the ladder. Op byte-identical; make verify 143/0. Owed: a PPK2 measurement to quantify the skip-hold power saving over a long run (the cadence is correct now; the number is owner-gated).

11.2 dev.0.12 hall + dev.0.13 stall recovery — closing the op-parity gaps (2026-07-25)

A verify pass over the op function table (Sten: "verify all op functions are implemented") found the 8 dropped op funcs all reimplemented per-pass, but two capability gaps:

dev.0.12 — hall monitored constantly (SWR-289 strict). The fold counted BP hall only in RUNNING + PARKING; the per-pass bp_drive_pass didn't stamp the ring the way op's bp_drive_window did, so DOSING/COAST/OFFSET/CAL were hall-blind. Fix: hoist bp_hall_edge_service to the top of the continuous loop — one call per pass, every state (counting unconditional; CPU-wake still gated to RUNNING; folded PARKING reads bp_hall_switch; op keeps its per-state call via #ifndef). On-board: a >1-rev dose ticked bp_hall_revolutions 0→1 at ~5184 edges while bp_state==DOSING.

dev.0.13 — non-blocking stall power-cycle. Folded RUNNING re-kicked a mid-run stall immediately; op regulate_pump first power-cycles the DAC7574 driver (DAC-halt + motor/encoder off + 200 ms) to clear a latch (bp_dead_after_crash). Fix: seg_recover() does the halt + a seg_t.recover_until deadline; the stalled pump's own drive is held off for the 200 ms (sched_idle treats it like a skip-hold), then the per-pass kick re-drives.

"Sleeps through" is the wrong word — the loop is NOT suspended for 200 ms (Sten asked exactly this: "do we not service the AC pump then during that sleep?"). The recovery deadline gates only the recovering pump's own drive. The main loop keeps running: ac_tick() and bp_tick() are still called every pass and hall is still serviced at the loop top. If the OTHER pump is measuring, the loop spins at full rate and that pump is serviced with zero added latency; if nothing else has work, sched_idle() returns true and the loop sleeps one wake period (~1 ms) at a time, re-servicing both pumps on every wake. So the AC is never starved — and this is strictly BETTER than op, whose regulate_pump sat in a genuinely blocking 200 ms delay with the AC unserviced throughout.

Dose/park keep the immediate re-kick (matching op — only op RUNNING power-cycled). Headroom 620 B; cal enc_total 5184 in-gate; op byte-identical; no false recovery in a normal BP+AC run. (A real mid-run driver latch can't be forced on the bench; the path is op-parity + proven not to false-trigger.)

12. PROMOTION TO OPERATIONAL — op 1.17.0 (2026-07-26)

Owner call ("promote to operational"), taken because the promoted binary is the one that actually ships: a TestOp run validates the logic, but only the operational image validates the artifact, its headroom, and its contract with the real firmware.

12.1 How it is switched

One macro, defined near the top of main.c:

#if !defined(ULP_TEST_BUILD) && !defined(ULP_TEST2_BUILD)
#define ULP_FOLD_BUILD 1
#endif

All 24 fold guards were renamed ULP_TESTOP_BUILD → ULP_FOLD_BUILD, so the fold now compiles into both the operational binary and the TestOp image. Rollback is that one line — commenting it out restores the 1.15.0 per-wake tick + blocking windows, which remain in the file under #ifndef ULP_FOLD_BUILD. Deliberately NOT promoted (still #ifdef ULP_TESTOP_BUILD): the three vestigial DEFEND_CLOCK blocks (the soc/sens_reg.h include, the no-op macro, its call site) — that is the retired #48 defense and the convicted #53 cause, and it stays out of the operational image. The switch is scoped away from pump_test/pump_test2, which exclude the regulation entirely; letting fold state link into them would shift their maps for code they never run.

12.2 Calibration — the firmware contract is UNCHANGED

The fold replaced the blocking test_determine_parking() with the non-blocking BP_PARK_CAL state, which the Control app drove via bp_park_calibrating. The firmware's _state_calibration, however, calibrates by writing test_request = TEST_DETERMINE_PARKING and then polling for TEST_NONE. So as the operational binary the fold answers that contract directly:

  • BP_IDLE enters BP_PARK_CAL on bp_park_calibrating || test_request == TEST_DETERMINE_PARKING (both triggers converge on the one flag, so the exit paths stay single-path);
  • every exit — cancel, 30 s deadline, success, sweep-fail — clears test_request = TEST_NONE. This is required twice over: it is the firmware's completion signal, AND leaving it set would re-trigger calibration from BP_IDLE on the very next pass (an endless cal loop).

Published results are unchanged: bp_hall_bracket_ticks, bp_park_offset_ticks = bracket/2 (SWR-119/120), bp_park_enc_total. No firmware change is needed.

On the 596 B headroom warning. build_verify_ulp.py warns under 768 B and fails under 512 B, so 596 B is a warning, not a failure — and the 1.15.0 binary this replaces sits at 568 B, i.e. the warning is inherited, not introduced, and the fold improves it. The number also understates the change: headroom is the space the call stack grows into, and the fold's whole point is that the deep bp_tick → bp_drive_window → regulate_pump → run_simple_p → i2c chain behind the #48 overflow class is gone — a flat loop needs less of that space than the chain it replaces. (For contrast, the quarantined 1.16.0 was 552 B, i.e. worse than baseline.) A live stack low-water measurement during calibration — the deepest operation — is the right way to convert this from an argument into a number, and is part of the deploy gate.

12.4 Deployment coupling (IMPORTANT)

The op symbol table changed: 4 added (BP_PARK_CALIBRATING, BP_CAL_PHASE/REV/BRACKET), 0 removed (so every name the firmware imports still resolves), 83 moved. Addresses shift on every build, so the binary and fluispotter/variables.py must be deployed together — shipping the new binary against the old map would point every mem32 access at the wrong address.
