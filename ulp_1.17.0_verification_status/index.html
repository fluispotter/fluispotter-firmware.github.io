Verification status — operational ULP 1.17.0 (the promoted cooperative scheduler)

Build under assessment: operational pump_regulator.bin, ULP 1.17.0, 7088 B, 596 B stack headroom, built from main.c with ULP_FOLD_BUILD defined. Assessed: 2026-07-26. Question asked: which requirements have NOT been verified on the new build?

make verify reports 143 PASS / 0 FAIL / 22 NOT-TESTED (305 tests). That headline is true but not sufficient, because a green suite can still be green for the wrong reason. The three categories below separate what is genuinely evidenced for 1.17.0 from what is not.

A. The headline gates — verified on this build

Gate Evidence
ULP builds, sized, no forbidden libgcc helpers build_verify_ulp.py: 7088 B, libgcc=[]
Address maps match the built ELFs (op + test + test2) variables drift gate OK (all three were stale before this change)
Operational binary artifact matches source byte-identity check YES
Requirement registry / doc / lock discipline SWR-501, 502, 503, 508, 509, 510, 511, 512, 513, 514 PASS
ULP version discipline ulp_version reads 1.17.0 on-board and in the hub log

B. THE REAL GAP — 7 requirements that PASS but do not verify the shipping binary

verification/tests_sw/test_ulp_source.py verifies the ULP by static analysis of the source text of main.c. The promotion did not delete the old blocking implementation — it left it in place under #ifndef ULP_FOLD_BUILD so the rollback stays one line. So those functions are still in the file and the tests still find them and still pass — but they are compiled out of the binary we ship.

These requirements are therefore not evidenced for 1.17.0; their automated evidence describes the rolled-back 1.15.0 path:

Requirement Test asserts on (compiled out of 1.17.0)
SWR-109 ac_busy_hall_service
SWR-116 regulate_pump
SWR-126 regulate_pump, sample_encoder, try_kick_start
SWR-127 bp_drive_window
SWR-128 bp_drive_window
SWR-271 ac_busy_hall_service, ac_busy_regulate, bp_drive_window, try_kick_start
SWR-289 ac_busy_regulate, bp_drive_window

Also: TestAdaptiveKickStart.setUpClass binds try_kick_start, so every test in that class is analysing the retired kick rather than the per-pass try_kick_pass that 1.17.0 actually uses.

Important distinction. This does not mean the requirements are violated. In most cases the fold satisfies the intent more strongly than the code being asserted on — SWR-271 (AC must be serviced during BP operations) is the clearest example: the fold services ac_tick() on every loop pass in every state, which is strictly better than the ac_busy_regulate hack the test looks for. SWR-289 likewise: hall is serviced at the top of every pass in every state, versus the per-window calls the test asserts. What is missing is evidence, not necessarily conformance.

Recommended remedy (requires owner sign-off — the registry is locked, SWR-511): re-point these tests at the fold constructs (seg_pass, try_kick_pass, the loop-top bp_hall_edge_service, sched_idle) and, better, make the source tests build-aware so they analyse only the code that survives ULP_FOLD_BUILD. Until that is done, treat these 7 as unverified on 1.17.0 regardless of the green suite.

C. Requirements with no automated verification at all (22 NOT-TESTED)

Unchanged by this promotion — these were already NOT-TESTED — but several are exactly the behaviours the fold rewrote, so they matter more than usual here.

Bench/hardware (MECH) — the fold rewrote the code behind all of these: SWR-111 (no-start kick escalation), SWR-113 (running-stall recovery), SWR-120 (park at hall-zone centre), SWR-121 (dose handshake with coast capture), SWR-122 (AC bench convergence), SWR-123 (BP bench convergence), SWR-124 (AC slow-setpoint stability), SWR-125 (live sensors).

Deploy/self-test (MECH): SWR-504, SWR-505, SWR-506, SWR-507.

Software, untested: SWR-240, SWR-242, SWR-282, SWR-284, SWR-293 (WITHDRAWN), SWR-298.

Hub REST (separate repo): SWR-401, SWR-402, SWR-403, SWR-404.

D. What the live 20-sample dry run contributes

Run 2026-07-25-001 (see testlog/) is the first session-level evidence for 1.17.0 and covers, as live rather than static evidence:

  • Calibration — the rewired test_request = TEST_DETERMINE_PARKING → BP_PARK_CAL → TEST_NONE contract, driven by unmodified firmware (SWR-119/120/129 territory). Already observed: passed on attempt 2, failed attempt 1 with bp-no-full-rev — logged as a major deviation, not yet root-caused.
  • Dose + park + coast per sample ×20 (SWR-121 territory), BP/AC regulation (SWR-122/123), kick escalation from the parked dead-point (SWR-111/132).
  • Hall/deque completeness with DEQUE_AUDIT=1 already enabled on the board (SWR-289) — the live counterpart to the static evidence lost in category B.
  • Stability: reboot/WDT count with USB detached, so any reset is a real finding and not the known #46 USB-attached bench artifact.

A clean 20/20 does not close category B — static evidence and live evidence answer different questions — but it is the strongest available evidence that the promoted scheduler performs the operations those requirements govern.

Bottom line

  • Nothing FAILS.
  • 7 requirements (SWR-109, 116, 126, 127, 128, 271, 289) are green against code the shipping binary does not contain — the one thing a reader of "143 PASS / 0 FAIL" would not guess, and the item that most deserves owner attention.
  • 22 remain NOT-TESTED, 8 of them bench behaviours the fold rewrote.
  • Fixing category B means editing requirement-tagged tests, which is owner-gated.
